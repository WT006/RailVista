\* 带 * 的偏差百分比为负或小（G217/G111 实测略超官方，因 DP 简化与并行段；G227 曾过串至 2613km，已用官方里程封顶修到 550km）。

**根因**（不是算法 bug，是数据源特性）：OSM 中大量路段**不带 ref 标注**（尤其城市过境段、
新建改线段），`way["ref"~"(^|;)G318(;|$)"]` 查询只能取到带标注的段，贪心串接在无标注处断链，
形成「东一段西一段」。当前 `chainAll` 只保留最长主链，其余 orphan 段**丢弃**。

### 2.2 改进方向（P0，按性价比排序）

1. **多段几何存储**（结构性修复，建议先做）：`RoadGeometry` 增加 `segments?: RoadPoint[][]`，
   `chainAll` 的 orphan 链不再丢弃而是按里程排序存入 segments；`/api/drive/road/:key` 与
   `planRoadRoute` 输出时把 segments 拼接展示（段间断点如实标注「未贯通 N km」）。这样即使
   ref 标注不全，也能把已知的每一段都画出来，G318 立刻从 1954km 涨到接近全量。
   改动点：`scripts/fetch-road-geometry.mjs`（chainAll 返回全部链）、
   `packages/shared/src/types.ts`（RoadGeometry.segments）、
   `apps/api/src/services/roadNetwork.ts`（overview/road 输出）、`roadRouting.planRoadRoute`。
2. **route relation 优先**：多数国道在 OSM 有完整的 route relation（`rel["route"="road"]["ref"="G318"]`），
   成员覆盖比散 way 全。当前 lib 里 relation 是 ways ≥3 失败后的**回退**；对长线可反转优先级
   （relation 命中即直接按成员顺序串接 + bbox 过滤）。注意 PRD 附录 A8：relation 的 `>;out geom`
   会展开全国整条，必须按 bbox 过滤 member 后重新串接。
3. **按省分片抓取**：单条全国查询易超时/限流；按省 bbox 分片（34 次/条）命中率高且可断点续抓
   （缓存天然支持）。PRD §3.4 Step 2 本来就是这个设计。
4. **补 ref 缺口**：对断链点做局部 Overpass 查询（around:2000 找连接 way，不限 ref），
   只补「几何上确实连通」的段，宁缺毋滥（诚实纪律）。
5. **跳点修复**：verify 已能区分「DP 简化的笔直长段」（青藏线柴达木段笔直几十公里，非错误）
   与「真跳点」（>5km 且方向突变 >25°）。真跳点多为 5km 拼接容差留下的折线弯，可在 simplifyDP
   前先做 splice 平滑或收紧 attach 容差到 3km。

### 2.3 Overpass 使用纪律（血泪经验，必须遵守）

- **必须带 User-Agent**；4 端点 failover：`maps.mail.ru`（最稳）→ `overpass-api.de` → `overpass.osm.ch` → `overpass.kumi.systems`（已内置在 `scripts/lib/overpass.mjs`）
- **限流真实存在**：连续抓 15 条左右会出现整端点 0 ways / HTTP 504（G109、G331、G314 都中过招）。
  对策：失败后 sleep 60s 重试该条；大批量抓取时每 5 条 sleep 30s
- **缓存**：`data/cache/roads/ways-{ref}.json` 命中即跳过网络；改串接算法后重跑是**零网络成本**的
  （所有已抓数据的 way 缓存都在）
- `geometry` 是 `{lat,lon}` 对象数组，lib 已转 `[lng,lat]`
- 多编号共线 way 的 ref 形如 `"G318;G214"`，查询必须用正则 `(^|;)G318(;|$)`（已内置）

### 2.4 拓扑质量

当前 RVRT 40,448 节点 / 44,710 边，**24 个连通分量、主分量仅 17,919 节点**——因为几何是部分段，
段与段之间不接触。多段几何 + relation 全量展开后主分量占比会大幅提升；跨线边阈值（1km）在
`build-road-topology.mjs` 的 `CROSS_LINK_KM` 可调。A* 已验证可用（独山子→库车 507km 走 G217）。

## 六、环境与踩坑备忘（Windows + 本仓库）

1. **PowerShell**：`pnpm`/`npm` 须用 `pnpm.cmd`/`npm.cmd`（执行策略拦 .ps1）；不支持 heredoc，
   提交信息用 `git commit -F 文件`；行内 node -e 的引号会被 PowerShell 改写——**复杂命令一律写临时 .mjs/.cjs 文件再 node 执行**
2. **BOM 陷阱**：PowerShell `Set-Content -Encoding utf8` 会写 BOM 破坏 package.json 的 vite 解析；
   改 JSON 一律用 node 脚本 `fs.writeFileSync`
3. **沙箱**：仓库兄弟目录只读（worktree 验证法不可用，改用「备份→HEAD 版本→跑测试→还原」法）；
   Edge 探针清理时的 CLIXML 报错是噪音，看 stdout 的 JSON 即可
4. **测试基线**：shared 174/174 全绿；`pnpm --filter @railvista/api test` 有 **9 个预先存在的铁路侧失败**
   （corridors/osmRailway/scenicSpots，依赖实时 Overpass 与另一任务的 WIP 数据，与 drive 无关，
   已用 HEAD 数据 A/B 验证过），不要试图在路网任务里修它们
5. **工作区红线**：`data/presets/scenic-spots.json`、`data/stations-geo.json`、
   `scripts/build-scenic-spots-curated.mjs` 的未提交改动 + 一批纪念票模板文件**属于另一个进行中的任务**，
   提交时用显式文件列表（git add <paths>），严禁 `git add -A`
6. 大文件策略：`data/roads/china-road-topo.bin` 按铁路 bin 同政策 gitignore（脚本可重建）；
  `data/cache/roads/` 已整体 gitignore
