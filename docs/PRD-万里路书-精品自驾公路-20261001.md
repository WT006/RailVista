## 一、政策依据与产品定位

### 1.1 政策原文要点（已核实）

来源：交通运输部《精品自驾旅游公路实施方案》政策解读（2026-08-17 发布，公路局）

- 文号：**交公路发〔2026〕100 号**
- 体系：**「1+N」精品自驾旅游公路体系**
- 主体：**以普通国道为主体**（不是高速！这点决定了我们的路网数据口径必须优先 trunk/primary，而非 motorway）
- 原则：总体骨架保持稳定、重要区域拓展支线、局部路段多元路径
- 骨架：**「三环、四横、五纵」**，总里程约 **6 万公里**
- 目标：2030 年跨区域长距离路线基本形成、优良路率高于平均、重点路段成为自驾知名目的地；2035 年「1+N」体系全面形成
- 五项重点任务：完善基础设施（观景/安全设施）、健全服务体系（租车/跨省运车/充电/快修/装备租赁）、强化安全智慧（跨部门应急联动、数智化救援、**交通文旅数据共享**）、创新产品业态（公路文化体验、"公路+"露营研学赛事、联票套票停车接驳）、加强精细管理

> **对产品的直接启示**：政策明确提到"推动交通、文旅等部门数据共享，系统分析自驾出行特征及需求"，以及"完善观景设施"。我们的**小确幸点位库**本质上就是"观景设施+文旅资源"的数字化映射，**车速感知提醒**对应"强化安全智慧"，**轨迹路书**对应"公路文化体验"。产品与政策高度同频，具备申报/合作叙事空间。

### 1.2 官方 12 条主干线（政策原文名单，与需求方表格完全一致）

| 类别 | 线路名称 | 需求方定义的核心标签 |
|---|---|---|
| **三环** | ① 沿边沿海环线 | 国境线、G331、极地到热带 |
| | ② 首都都市圈环线 | 草原、长城、皇家园林 |
| | ③ 青甘环线 | 大漠、盐湖、石窟、祁连山 |
| **四横** | ④ 长城文化 | 从山海关到嘉峪关，长城全程 |
| | ⑤ 黄河文化 | 从入海口到三江源，母亲河全程 |
| | ⑥ 长江文化 | 从崇明岛到金沙江，长江全程 |
| | ⑦ 西部雪域天路 | G318/G317，川藏 + 滇藏 |
| **五纵** | ⑧ 大运河文化 | 京杭大运河全程 |
| | ⑨ 华东世界遗产 | 泰山 - 黄山 - 武夷山，世遗串联 |
| | ⑩ 中部锦绣山岳 | 张家界 - 武当山 - 神农架 |

### 1.3 产品定位：与铁路版错位

```
RailVista 铁路版      →  我此刻在铁路的哪里（固定线路、固定时刻表）
万里路书 · 自驾版     →  我正在自驾的这条路上，前方有什么（自由线路、无时刻表）
```

关键差异带来的设计约束：

| 维度 | 铁路版 | 自驾版 |
|---|---|---|
| 路线 | 预置 248 走廊，时刻表驱动 | 预置 12+N 线路，**可自由偏离**，需路网匹配 |
| 定位 | 车次 + ETA 推算进度 | 纯 GPS，需投影到路线求里程桩 |
| 方向 | 固定（上行/下行） | **任意**，需 heading 判定正反向 |
| 速度 | 图定速度 | **实时车速**，直接决定推送策略 |
| 停留 | 站停分钟 | 任意停车，需驻留检测 |
| 交互 | 被动观看 | **主动决策**（要不要减速/停车） |

### 1.4 差异化壁垒

市面上的自驾产品（高德/百度地图）解决的是"怎么到"，不解决"路上有什么值得停"。
本产品的独占价值 = **小确幸点位库**（人工+AI 生产、带里程桩和左右侧、带"怎么玩"），这是地图厂商不会做的重内容资产。

### 4.1 ① 小确幸雷达

#### 输入与输出

```ts
// 输入
interface RadarInput {
  gps: GpsSample;              // lng/lat/speed(m/s)/heading(deg)/accuracy
  route: DriveRoute;           // 当前线路（已含 geometry + cumKm）
  highlights: DriveHighlight[];
  /** 自由行驶时为 true，需先做路网匹配 */
  freeDrive?: boolean;
}

// 输出
interface RadarResult {
  /** 主卡片：前方最近的一个合适点位 */
  primary: RadarHit | null;
  /** 次卡片：再往后的一个，做"下下个"预告 */
  secondary: RadarHit | null;
  /** 已错过（刚过身后的），给"你刚错过"提示 */
  missed: RadarHit | null;
  /** 当前里程桩 */
  alongKm: number;
  /** 行驶方向 */
  direction: 'forward' | 'backward' | 'unknown';
  /** 当前车速带 */
  band: SpeedBand;
  /** 距路线偏离距离（m），用于判断是否已偏离 */
  offRouteM: number;
}

interface RadarHit {
  highlight: DriveHighlight;
  /** 前方还有多远（km） */
  aheadKm: number;
  /** 按当前车速预计到达秒数 */
  etaSec: number | null;
  /** 卡片文案，直接可渲染 */
  cardText: string;     // '前方 3.2 公里・小确幸：无人雅丹观景点'
  /** 是否已进入强提醒半径 */
  notify: boolean;
  sideText: string;     // '右侧' | '左侧'
}
```

#### 算法（前端本地计算，禁止走网络往返）

```ts
function computeRadar(input: RadarInput): RadarResult {
  const { gps, route, highlights } = input;
  const speedKmh = (gps.speed ?? 0) * 3.6;

  // 1) 投影：把 GPS 投到路线折线上，得到里程桩与偏离距离
  const proj = projectToPolyline(route.geometry, route.cumKm!, gps);
  // → { alongKm, offRouteM, segIndex, tangentHeading }

  // 2) 判定行驶方向：heading 与折线切向夹角
  //    |Δ| < 90° → forward；> 90° → backward；无 heading → unknown
  const direction = resolveDirection(gps.heading, proj.tangentHeading);

  // 3) 车速带
  const band: SpeedBand = speedKmh > 80 ? 'fast' : speedKmh < 40 ? 'slow' : 'cruise';

  // 4) 候选筛选：沿行驶方向取前方 lookahead 内的点位
  //    车速越快看得越远：lookahead = clamp(speedKmh * 0.05, 3, 15) km
  const lookaheadKm = Math.min(15, Math.max(3, speedKmh * 0.05));
  const candidates = highlights
    .filter((h) => aheadKmOf(h.alongKm, proj.alongKm, direction, route.totalKm) <= lookaheadKm)
    .filter((h) => directionMatch(h.direction, direction));

  // 5) ★ 车速感知过滤（需求方明确规则）★
  const filtered = candidates.filter((h) => {
    if (band === 'fast')  return h.worthSlowDown;       // >80 只推「值得减速」
    if (band === 'slow')  return h.canPark;             // <40 只推「可以停车」
    return h.worthSlowDown || h.canPark;                // 40~80 两者都推
  });

  // 6) 排序：先按 worthSlowDown 权重，再按距离
  //    高速时"值得减速"的点必须优先，否则会一闪而过
  const sorted = filtered.sort((a, b) => {
    if (band === 'fast' && a.worthSlowDown !== b.worthSlowDown) {
      return a.worthSlowDown ? -1 : 1;
    }
    return aheadKmOf(a.alongKm, ...) - aheadKmOf(b.alongKm, ...);
  });

  // 7) 生成卡片
  const primary = sorted[0] ? toHit(sorted[0]) : null;
  const secondary = sorted[1] ? toHit(sorted[1]) : null;

  // 8) 强提醒：进入 notifyM（默认 500m）半径
  if (primary) primary.notify = primary.aheadKm * 1000 <= (primary.highlight.notifyM ?? 500);

  // 9) 错过检测：身后 0~1km 且有 worthSlowDown 的点
  const missed = findMissed(...);

  return { primary, secondary, missed, alongKm, direction, band, offRouteM: proj.offRouteM };
}
```

#### 关键设计决策

| 决策 | 理由 |
|---|---|
| **雷达在前端算** | 1s 级刷新，网络往返不可接受；且隧道无信号时必须可用（政策明确"智慧安全"） |
| **用里程桩而非直线距离** | 公路是弯的，直线距离会严重误判沿边沿海这类折线；里程桩才是"前方 3.2 公里"的正确语义 |
| **lookahead 随车速伸缩** | 120km/h 时看 6km（约 3 分钟），20km/h 时看 3km，符合驾驶心理 |
| **高速时 worthSlowDown 优先于距离** | 否则高速下最近的普通点位会挤掉真正"错过可惜"的 |
| **missed 提示** | 自驾不能掉头是常态，明确告知"你刚错过"比沉默更友好，也为下次做种草 |

#### 推送与卡片（Web beta）

- Web 端用 **Notification API**（需用户授权）+ 页面内 `DriveRadarCard` 双通道
- 鸿蒙端用 **锁屏卡片 / 实况窗**（`FormExtensionAbility`）+ 推送通知，卡片文案格式保持一致：
  `前方 3.2 公里・小确幸：无人雅丹观景点`
- **节流**：同一 highlight 只推一次；离开 1km 后重置；60s 内最多 1 条

### 4.3 ③ 轨迹自动记录

**只记关键点**（需求方明确要求省电省流量）：

| 触发条件 | 记录类型 | 说明 |
|---|---|---|
| 开始记录 | `start` | 起点 |
| 位移 > 500m 且距上个点 > 120s | `pass` | 抽稀轨迹，1 小时高速约 12~24 个点 |
| 速度 < 5km/h 持续 > 5min | `stay` | 记录 `dwellMin`、位置 |
| 进入 highlight 半径 100m | `checkin` | 自动打卡，关联 `highlightId` |
| 跨章节边界 | `chapter` | 标记路书章节进度 |
| 结束记录 | `end` | 终点，汇总 totalKm / driveMin |

**数据量**：一次 7 天青甘环线约 **150~300 个关键点**，JSON < 60KB。对比每秒记录（约 60 万点）省 99.95%。

**存储**：
- Web：`localStorage` key `railvista.drive.tracks`（配合现有 `lib/persistTrip.ts` 的模式）
- 鸿蒙：`Preferences`（当前轨迹）+ `RelationalStore`（历史路书）

**后台保活**（鸿蒙）：`backgroundTaskManager` 的 `LOCATION` 模式 + 长时任务；Web 端用 `visibilitychange` 降级为前台记录。

**结束自动生成路书**：`end` → 按时间排序关键点 → 关联 highlight 的 `intro`/`howToPlay`/照片 → 生成 `MyRoadbook`，可编辑标题/文案/封面、可分享（`shareSlug`）。

### 4.4 ④ 车速感知提醒

**三种来源**：

1. **预置 `RoadAlert`**（数据驱动）：景观路段、落石、长下坡、无信号 —— 来自线路数据
2. **实时计算**（算法驱动）：
   - **连续弯道**：取前方 2km 折线，累计转角 > 120° → `curve`
   - **长下坡**：前方 5km 高程下降 > 200m → `steep`（需高程数据）
   - **高海拔**：当前点高程 > 3500m → `altitude`
3. **车速联动**：当前车速 > `suggestSpeedKmh` + 15 时，提醒条变红

**提醒条文案模板**：

| kind | 文案 |
|---|---|
| scenic | 前方 10 公里为景观路段，建议减速慢行 |
| curve | 前方 3 公里连续弯道，建议车速 40 |
| steep | 前方 20 公里长下坡，低挡位控速，避免刹车过热 |
| altitude | 当前海拔 3648 米，注意高原反应，避免剧烈运动 |
| rockfall | 落石路段，请勿停车观望 |
| nocell | 前方 30 公里无手机信号，建议提前下载离线路书 |

**高程数据**：优先级 —— ① 路书 build 时一次性从公开高程 API 采样写入 `geometry` 的第三个元素 `[lng, lat, elev]`（推荐，离线可用）；② 运行时调用（不推荐，无信号区失效）。
> 建议采用 ①，`geometry` 扩展为 `[lng, lat, elev?]`，向后兼容（现有代码读前两位不受影响）。

## 五、数据生产流水线（技术核心）

### 5.1 总体思路：不做全路网，做「按编号成链」

**关键洞察**：OSM 里国道/省道带 `ref` 标签（如 `ref=G318`），可以**按编号精确抓取**，无需下载并构建中国全量公路网（那会是几十 GB 且质量不可控）。

```
roadRefs: ['G109','G315','G3011','G30','G227']
        ↓ Overpass 按 ref 抓取 ways
        ↓ 端点最近邻串接成链（容差 300m）
        ↓ 按 waypoints 顺序裁剪/排序
        ↓ Douglas-Peucker 简化（容差 30m）
        ↓ 计算 cumKm + 采样高程
        ↓ 回写 drive-routes/<id>.json
```

**优势**：数据量小（一条线几千个点）、准确（真实国道走向）、可增量的（换一条线重抓即可）、无需路网拓扑引擎。

**劣势**：路网"连通成网"（需求方提到的"连成公路网"）需要额外做。解决方案见 §5.4。

### 5.2 OSM 抓取规格

```
[out:json][timeout:180];
area["name"="中国"]->.a;
(
  way["highway"~"^(motorway|trunk|primary|secondary|tertiary)$"]["ref"="G318"](area.a);
);
out geom;
```

**等级映射表**（决定 `cls`）：

| OSM `ref` 前缀 | `cls` | 优先级 |
|---|---|---|
| `G` + 数字（1~3 位） | `G` 国道 | 高 |
| `G` + 4 位（如 G5611） | `E` 高速（国家高速） | 中 |
| `S` + 数字 | `S` 省道 | 高 |
| `X` + 数字 | `X` 县道 | 中 |
| `Y`/`C` + 数字 | `Y`/`C` | 低 |
| 无 ref 但 `highway=trunk` | `G`（无名国道） | 兜底 |

**端点串接算法**：
1. 所有 way 视为有向线段，建端点哈希（坐标量化到 1e-5，约 1m）
2. 度为 1 的端点作为链头候选
3. 从链头出发，每次找与当前端点距离 < 300m 的未访问 way 接上；way 内部必要时反转
4. 断开处（>300m）标记为 `gap`，写入构建报告**必须人工复核**（历史上铁路走廊 ingest 的最大教训就是断点，见 `docs/corridor-ingest-lessons.md`）

**分片**：按省份 bbox 分片抓取，避免 Overpass 超时；复用 `apps/api/src/services/overpassTracker.ts` 的限流与重试。

### 5.4 「连成公路网」的两阶段

| 阶段 | 做法 | 适用 |
|---|---|---|
| **阶段 A（beta）** | 上述"按编号成链"，12+N 条线各自独立成线 | 路书、雷达、轨迹全都能跑，95% 场景够用 |
| **阶段 B（联网）** | 把 A 阶段抓到的所有 ways 合并去重，构建 **CSR 图**（直接复用 `railTopology.ts` 的 `RVTP` 二进制格式 + Dijkstra），实现：任意两点驾车路径规划、自由行驶时的路网匹配（map matching）、断链自动补全 | 自由行驶模式、用户自定义路线 |

> **复用点**：`railTopology.ts` 已有 CSR 加载、0.03° 网格索引、Dijkstra、边权系数（typePenalty/lineBonus）。阶段 B 只需把"铁路线名命中"换成"公路 ref 命中"，边权换成"公路等级 + 限速"，几乎不用重写图算法。**这是本项目最大的一处资产复用。**

### 5.5 校准与质量门禁

参考 `docs/corridor-calibration-plan.md` 与 `docs/scenic-schema-v3.md` 的既有规范：

| 检查项 | 门禁 | 处理 |
|---|---|---|
| 断链 gap 数 | = 0 | 人工补 waypoint 或换线 |
| 主线里程误差 | 与公开里程偏差 < 8% | 复核 roadRefs |
| 连续点间距 | 中位数 < 500m，最大 < 5km | 重抓该段 |
| 高程单调性 | 无 > 300m/点的跳变 | 高程源异常 |
| 小确幸里程桩 | 与最近路线点距离 < 300m | 坐标需贴线校准 |
| 小确幸左右侧 | 必须非 `unknown` | 用 heading 与切向叉积计算，复用 `spotSide` 逻辑 |
| 章节区间 | 覆盖完整、无重叠、无空洞 | 脚本校验 |

### 5.6 全国公路网索引层：从「12 条精品线」到「全国线路可查」

> **需求方核心追问**：12 条线能保证全国 G/S/X 所有线路可查吗？
> **答案：不能。12 条线是"精选层"，不是"底盘"。** 本节给出升级为「全国可查」的完整方案。

#### 5.6.1 必须先正视的规模差距（官方数据）

数据源：交通运输部《2024 年交通运输行业发展统计公报》（2025-06 发布）；《国家公路网规划》（2022，发改委+交通运输部）。

| 层级 | 官方里程（2024 年末） | 12 条精品线覆盖 | 覆盖率 |
|---|---|---|---|
| 国道 G | **38.67 万公里** | ~4.4 万公里（含线间共用路段） | **~11%** |
| 省道 S | **41.01 万公里** | 近乎 0 | **~0%** |
| 县道 X | **69.88 万公里** | 0 | **0%** |
| 乡道 Y | **124.34 万公里** | 0 | **0%** |
| 村道 C | **270.14 万公里** | 0 | **0%** |
| **全国公路合计** | **549.04 万公里** | **~4.4 万公里** | **0.8%** |

**结论：12 条线只覆盖全国公路的 0.8%、国道的 11%。** 它是"选出来的精华"，不是"查得到的全量"。要做「全国可查」，必须新增一层**全国路网索引**——这与 12 条精品线是**互补关系，不是替代关系**：

```
全国路网索引（底盘 = 可查）  ←  用户问的这一层
        ↓ 从中精选
12 条国家级主干线 + N 条省级精品线（精华 = 路书）  ←  已设计的这一层
```

#### 5.6.2 关键认知：「可查」≠「全渲染」

549 万公里的几何数据不可能一次性进前端。但**用户要的是"查得到"，不是"一次全画出来"**。因此拆成三层：

| 层 | 职责 | 数据规模 | 加载方式 |
|---|---|---|---|
| **L0 索引层** | 全国 G/S/X 的**编号 + 名称 + 起终点 + 里程 + 省份 + 几何可用标志** —— 「可查」的真正载体 | 约 3~5 万条 × ~200B ≈ **6~10MB** | **按省分片**（34 片），首屏只加载当前省 ~250KB |
| **L1 几何层** | 某条路的折线，LOD 三档（概览 1km / 详情 100m / 精度 30m） | 单条国道 100m 精度约 0.5~3MB | **按需加载** + 本地持久化缓存 |
| **L2 拓扑层** | CSR 图，支持任意两点路径规划、自由行驶匹配 | 复用 `railTopology.ts` RVTP 格式 | 阶段 B，服务端常驻 |

**L0 是本节新增的核心**。有了它，用户在搜索框输入 `G318` 或 `太行一号` 立刻出结果，点进去再拉 L1 几何。

#### 5.6.3 编号主键设计（重要技术细节）

**国道编号全国唯一，省道/县道/乡道/村道是省内编号、跨省会重复**（如 S101 在多省都存在）。因此：

```
G / 国家高速  →  主键 = ref            （如 G318、G5611）
S / X / Y / C →  主键 = province + ref  （如 山西:S101）
```

编号规则（用于解析与分级）：

| 模式 | 含义 | 示例 |
|---|---|---|
| `G` + 1~3 位数字 | 普通国道（12 放射 + 47 纵 + 60 横 + 182 联络 = **301 条**） | G104、G318 |
| `G` + 4 位数字 | 国家高速（7 放射 + 11 纵 + 18 横 + 6 地区环 + 12 都市圈环 + 30 绕城 + 31 并行 + 163 联络 = **278 条**） | G5611 |
| `S` + 数字 | 省道（省内唯一） | S216 |
| `X` + 数字 | 县道 | X301 |
| `Y` / `C` + 数字 | 乡道 / 村道 | Y012 |

#### 5.6.4 数据源现实与覆盖率（诚实评估）

**必须说清：不存在官方开放的「全国所有公路逐条几何」数据集。** 可行的是「权威名录 + 开源几何」组合：

| 源 | 提供什么 | 缺什么 | 用途 |
|---|---|---|---|
| 《国家公路网规划》（发改委+交通运输部） | 301 条国道 + 278 条国家高速的**权威编号与布局** | 无坐标几何 | **L0 索引的权威骨架** |
| 各省交通运输厅省道名录 | 省道编号、起终点、里程 | 无几何、格式不一 | L0 省道索引 |
| OSM / Geofabrik `china-latest.osm.pbf` | **几何 + `ref` 标签**；中国 motorway 段数约 46.6 万（全球第一） | 编号覆盖不全、西部稀疏 | **L1 几何主源** |
| Overpass API | 按 ref 精确抓取补全 | 配额与超时 | 增量补全 |
| 高德 / 天地图（项目已有 `map/amap.ts`） | 商业级几何与名称 | 配额、费用、许可 | 纠偏与兜底 |

**各层级几何可查率预估（OSM 为主源）**：

| 层级 | 编号可查（名录） | 几何可查（OSM） | 说明 |
|---|---|---|---|
| 国家高速 | ~100% | **90~95%** | OSM 中国高速覆盖最好 |
| 普通国道 G | **100%**（权威名录 301 条） | **85~95%** | ref 标签完整度高 |
| 省道 S | ~90% | **50~70%** | 东部好、西部稀疏 |
| 县道 X | ~60% | **20~40%** | 大量缺失几何 |
| 乡道 Y / 村道 C | ~30% | **<10%** | 建议**只做编号索引，不做几何** |

> **产品口径建议**：对外承诺「**国道全可查、省道基本可查、县道部分可查**」，不承诺乡村道几何。索引里对无几何的条目明确标注「暂无走向数据」，并提供「申请补全」入口（后续可接 UGC 投稿）。

## 七、景点体系：与 432 景点库的关系

现有 `scenic-spots.json`（432 处）是**铁路视角**（车窗可见、沿线、左右侧基于铁路方向）。自驾视角不同：

| 差异 | 处理 |
|---|---|
| 可见半径 | 铁路 15km；自驾观景点可达 50km（远山）→ highlight 独立设 `maxDistKm` |
| 左右侧基准 | 铁路按车次方向；自驾按**行驶方向**（可能反向）→ 运行时用 heading 叉积计算，不写死 |
| 可达性 | 铁路"看得到到不了"；自驾**必须能停车到达** → 新增 `canPark` / `walkMinutes` |
| 新增点位 | 公路视角的大国工程（大桥、服务区、隧道口、观景台）、路边奇观 → 新建 `drive-spots.json` |

**复用规则**：
- 432 库中坐标落在新线路 30km 内的，直接 `spotIds` 引用，**不重复生产**
- 432 之外的公路专属点位，写入 `drive-spots.json`，**字段与 `ScenicSpot` 完全兼容**（可直接被现有 `/atlas` 与图鉴模块消费）

## 十三、开放问题（需需求方确认）

1. **小确幸首期范围**：12 条线全量（约 500 条 / 20 人日）还是先 3 条精品线（约 120 条 / 5 人日）？
2. **公路数据来源**：OSM（免费、需清洗、国道覆盖尚可）还是商业地图 API（准确、有配额与费用）？建议 **OSM 为主 + 高德纠偏**（项目已有 `map/amap.ts`）。
3. **高程数据**：是否有可用的高程 API？若无，可先不做坡度提醒（M4 降级）。
4. **音频**：首期 TTS 兜底还是必须真人录音？真人录音 96 段的制作成本约 8~12 人日 + 录音资源。
5. **图片素材**：小确幸的照片从哪来？自有素材 / AI 生成 / UGC？影响版权与工期。
6. **官方线路表**：是否等待交通运输部发布逐桩线路走向后再定稿？（建议先按本文档骨架开发，留校准开关）
7. **【新增·关键】全国可查的范围与优先级**：先做 N1「国道全可查」（14 人日）还是直接 N1~N3「G/S/X 全可查」（38 人日）？建议先 N1。
8. **【新增·关键】几何数据源确认**：OSM 为主（免费、国道覆盖 85~95%、县道仅 20~40%）是否可接受？若要求县道也有高精度几何，必须引入商业地图数据（有费用与许可约束），预算与授权需先行确认。
9. **【新增】对外承诺口径**：是否接受「县道及以下仅提供编号索引、不保证几何」并在 UI 明确标注？这直接决定 N3 的工作量。
