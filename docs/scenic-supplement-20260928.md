## 3. 车窗观赏方位：自动判定算法

### 3.1 问题定义

`side` 不是一个静态属性：同一处景观，列车反向行驶时会掉到另一侧。
因此必须拆成两个部分存储：

- **静态部分**：`side`（`left` / `right` / `both`）+ `sideRefDirection`（该 side 是在哪个参考方向下算出来的）
- **动态部分**：运行时按实际车次行进方向查表/换算

### 3.2 参考方向约定（`sideRefDirection`）

| 取值 | 含义 | 适用 |
|---|---|---|
| `line_forward` | 走廊 `railway` 数组的顶点顺序（0 → n） | 绝大多数，写入时用它 |
| `toward_<站名>` | 面向某个终点站 | 走廊顶点顺序不明确的支线（如 `guangmeishan__west__leg1`） |
| `up_direction` | 上行方向（朝北京） | 京广、京九、京沪、京哈等有明确上下行之分的干线 |

**换算规则**：运行时若 `sideRefDirection` 与实际行进方向相反（点积 < 0），则 `left ↔ right` 互换；`both` 不变。

### 3.3 算法步骤（可直接实现）

输入：线路折线 `P[0..n]`（`[lng,lat]`）、景点坐标 `S`、以及运行时实际行程折线 `T`（可选，缺省用 `P`）。

```
1) 找最近投影：遍历所有线段 [P[i-1], P[i]]，取垂距最小的一段，得到
   - alongKm   = cumKm[i-1] + segKm * t          // 里程 ← 写入 lines[].alongKmFrom/To
   - distKm    = 垂距(km)                        // 写入 lines[].distKm
2) 局部 ENU 平面换算（避免单位陷阱，见 3.4）：
      latRef = (A.lat + B.lat) / 2
      Kx = 111.320 * cos(rad(latRef))            // 经度 1° 对应公里
      Ky = 110.574                               // 纬度 1° 对应公里
      d = ( (B.lng-A.lng)*Kx , (B.lat-A.lat)*Ky )    // 线路前行方向向量
      q = A + d * t                                  // 投影点
      v = ( (S.lng-q.lng)*Kx , (S.lat-q.lat)*Ky )    // 由投影点指向景点的偏移向量
3) 叉积定侧：
      cross = d.x * v.y - d.y * v.x
      cross > 0  →  left        // 沿 d 前进时 v 在其左手边
      cross < 0  →  right
4) 退化为 both 的条件（任一成立）：
      a) distKm <= 0.3 km（轨道上 / 列车正从景观上方或正侧通过，两侧都能看）
      b) 景观是"延展型"（同一线路上 alongKmTo - alongKmFrom > 10 km 的河流/山脉/平原段落）
      c) sideRefDirection 在运行时与实际方向相反且该点为延展型
5) 输出 { side, sideRefDirection, alongKm, distKm, confidence }
```

**几何自检**：`|cross| = |d| * distKm`（因为 v ⊥ d）。若不满足，说明第 2 步的 `Kx/Ky` 用了投影点而非 A 点的纬度做修正，必须按 §3.4 修正。

### 3.4 单位陷阱（本次实测踩到，务必注意）

第一版实现写成：

```js
const dLng = rad(b.lng - a.lng) * Math.cos(rad((a.lat + b.lat) / 2));
const dLat = rad(b.lat - a.lat);
const cross = dLng * xLat - dLat * xLng;     // 单位：rad²
if (Math.abs(cross) < 0.15 * distKm) side = 'both';   // ❌ rad² 与 km 比较
```

结果是**全部 133 条候选都被判成 `both`**。原因是 `cross` 是弧度平方、阈值的 `distKm` 是公里，量纲不同，判据恒真。
正确做法是把 `d` 和 `v` 都换算到**同一局部平面公里的 ENU 坐标系**再叉乘（§3.3 第 2 步），此时 `cross` 的量纲是 km²，`|cross| / |d|` 恰好等于 `distKm`，几何自洽。

### 3.5 边界情形决策表

| 情形 | 判定 | 理由 |
|---|---|---|
| 跨河/跨海大桥，景点即桥本身 | `visibility: on_track`，`side: both` | 列车在桥上，两侧无遮挡 |
| 隧道连续段 > 60 % 里程 | `bestView.blocked` 写入"隧道遮挡"，仍保留条目 | 允许偶发可见，但要在 UI 上降低权重 |
| 夜间通过且无景观照明 | `bestView.timeOfDay: day`，不标 `night` | 参考既有的 `nightOnly` 字段语义 |
| 站点停靠超过 3 分钟 | 侧别判定用**停站时的车头朝向**，并在 UI 上提示"停靠期间可见" | 停站时乘客会换边看 |
| 枢纽换向（如郑州/株洲/徐州） | 以纵横线段分别算一次，`side` 取 dominant，另一方向记入 `bestView.note` | 换向站点所在线段的方向可能翻转 |
| 复线并行（京广线 / 京广高铁相距 < 2 km） | 两走廊都写 `lines[]`，各自独立算 `side` | 实测同一景点在两线上的 `side` 可能相反 |
| 里程 > 10 km 的延展型景观（河流、平原、山脉） | `side: both`，并在 `lines[]` 里写 `alongKmFrom/To` 区间 | 用单点代表点定侧会失真 |
| 投影落在线路起终点之外（t 被 clamp 到 0/1） | 判 `both` + 标 `【复核】` | 说明点位在走廊覆盖范围外侧 |

### 3.7 自检方法（入库前必跑）

1. `|cross| / |d| - distKm < 0.01` → 几何自洽。
2. 抽 20 条人工核验：卫星图上画线，确认景点在列车前进方向的左/右侧。
3. 反向断言：同一线路取反向相连的车站重新计算，`left ↔ right` 必须全部互换、`both` 必须保持不变。
4. 连续性检查：同一走廊相邻就址班次的 `side` 在同一站点附近不应跳变，除非几何上确实拐弯 ≥ 45°。

## 4. 车窗方位：UI 展示方案

### 4.1 信息架构

```
TripMap / 车窗视图
├── 顶部：当前最接近站点 + 下一站 ETA
├── 中：地图（轨道 + 景点 pin，按左/右着色）
└── 底部：SpotApproachCard（到站前 3 分钟升起）
          ├── 名称 + honors 徽标行
          ├── SideBadge（左/右/两侧）
          ├── 里程条：你在 XX km，景点在 YY km（前进还差 ZZ km）
          └── 时段提示："现在逆光，建议留意 10 分钟后"
```

### 4.2 组件 1：`SideBadge`（侧别徽标）

- **形状**：一个半 filled 的列车剖面方块——左侧半边高亮 = 左窗；右半边高亮 = 右窗；两侧都高亮 = "两侧均可"。
- **文案**：`左窗` / `右窗` / `两侧`；附加 tooltip："判定基准：本线路正向（如贵阳方向）行驶"。
- **反向车**：当检测到车次方向 == `sideRefDirection` 的反向时，徽标里做一个 180° 的翻转动画，避免用户按图上方向误判。
- **不确定态**：`side: both` 且 `distKm > 8` 时显示虚线边框 + "方位待确认"，与"两侧均可"区分。

### 4.3 组件 2：`SpotApproachCard`（临近提醒卡）

- 触发：`progressKm ∈ [alongKmFrom - 5, alongKmTo + 2]` 且 daylight 允许。
- 内容优先级：名称 > 侧别 > 剩余距离 > honors > intro 首句。
- 自动淡出：`progressKm > alongKmTo + 2`。
- 夜行车：若 `bestView.timeOfDay === 'day'` 且当前为夜间，**不弹**，改为写入"本次错过"列表（行程结束后可导出）。

### 4.4 组件 3：地图侧

- 景点 pin 按 `side` 分色：左=蓝、右=橙、两侧=灰；`distant` 用空心 pin。
- 长按 pin 弹出迷你卡，含 `honors` 与来源数量（`sources.length`），点"查看来源"跳 `sources[].ref`。
- 线路走廊层新增" 里程刻度"辅助线，用于人工复核 `alongKm`。

### 4.5 数据契约（前端）

```ts
interface ScenicSpotView {
  id: string; name: string;
  side: 'left' | 'right' | 'both';
  sideConfidence: 'high' | 'low';          // distKm<=0.3 或 延展型 → low
  sideRefDirection: string;
  flipped: boolean;                         // 当前车次方向是否触发了翻转
  alongKmFrom: number; alongKmTo: number;
  distKm: number; visibility: string;
  honors: string[]; viewMinutes: number;
  bestView: { months: number[]; timeOfDay: string; note?: string; blocked?: string[] };
  sourceCount: number;
  verificationStatus: 'verified' | 'probable' | 'unverified';
}
```

### 4.6 无障碍与暗色

- `SideBadge` 的左右不得只靠颜色区分——必须同时有**文字**和**箭头图标**（← / → / ↔）。
- 暗色模式：左 `#5B8DEF`、右 `#F2A33C`、两侧 `#8A8F98`，均需满足 4.5:1 对比度。

### 4.7 埋点与回归

| 埋点 | 用途 |
|---|---|
| `spot_card_shown` / `spot_card_dismissed` | 统计误报率 |
| `side_badge_tap` | 观察用户对侧别的困惑程度 |
| `side_override_report` | 用户提交"实际在另一侧"，直接回灌 `verification.method` |

## 10. 入库流程与验收（确认后再执行）

### 10.1 批次划分

| 批次 | 内容 | 目标文件 | 准入条件 |
|---|---|---|---|
| **A** | §5 中状态为"候选"的条目（约 60 条） | `_scenic-staging.json` → `scenic-spots.json` | 坐标换用 S/A 级来源；≥1 条 S/A + 1 条独立二源 |
| **B** | §6 中状态为"候选"的条目（约 45 条） | 同上 | 同上 |
| **C** | §7 重复命中 + 既有 432 条补 `side`/`dimensions` | 原地修改 `scenic-spots.json` | 用 §3 算法批算 `side`，跑反向互换断言 |
| **D** | §8 高校 79 所 | `_scenic-staging.json` | §8.1 距离门槛 + 官网/POI 双源 |

### 10.2 执行步骤

1. **生成 staging**：把 A/B/D 批次写入 `data/presets/_scenic-staging.json`（不进主库）。
2. **来源核验**：按 `docs/prompts/scenic-spots-generate.md` 的热/冷门检索模板逐条补源；冷门线路优先走人民铁道网、铁路官方线站资料、地方政府/文旅局公告。
3. **几何复核**：重跑投影脚本，确认 `alongKm / distKm / side` 与本文表格一致（`|cross|/|d| == distKm`）。
4. **批次升级**：
   ```bash
   pnpm --filter @railvista/api exec node scripts/build-scenic-spots-curated.mjs --ingest-staging
   ```
5. **C 批次补字段**：对既有 432 条批量赋值 `lines[]`（取最近走廊）、`side`、`sideRefDirection: line_forward`、`maxDistKm`（显式，按 visibility 取 3/8/35 或保留原值）。

### 10.3 验收断言

| 断言 | 通过标准 |
|---|---|
| 空白走廊清零 | 宽口径空白走廊数从 41 → ≤ 10（短支线允许留白） |
| 偏少走廊提升 | 本文点名的 20 条偏少走廊，每条 ≥ 8 点 |
| 反向互换 | 随机抽 50 条，反向计算后 `left ↔ right` 全部互换、`both` 全部不变，成功率 100 % |
| 来源门槛 | 入库条目中 `verification.status ∈ {verified, probable}` 占比 100 %；`unverified` 一律不出现在 `scenic-spots.json` |
| 坐标系统一 | 随机抽 30 条，与高德 POI 反查比对，偏差 < 200 m（即确为 WGS84 而非 GCJ02） |
| 无重复 | 任意两点距离 < 500 m 且语义相同的条目数为 0 |
| 六维回填 | `category === 'other'` 的条目 ≤ 80 条（当前 196） |

## 11. 风险与回滚

| 风险 | 影响 | 应对 |
|---|---|---|
| 坐标为初值，直接入库会污染数据 | 地图 pin 偏移几公里 | 严格执行 staging 隔离；`unverified` 不进主库 |
| 并行线导致 `side` 误判 | 提醒用户看错边 | 同一铁路的多条走廊在 `lines[]` 里各自独立存储 `side`；UI 上显示当前运行的是哪条线 |
| `both` 判定过宽 | 提醒卡价值下降 | `side=both` 且 `distKm>8` 时在 UI 上降级为"方位待确认"，不做弹窗 |
| 高校作为景点会稀释内容质量 | 用户观感变差 | 高校默认不参与临近提醒，仅在"城市名片"里出现；只有 ≤3 km 且有标志建筑的才可升级为提醒项 |
| 批量改既有 432 条造成回归 | `filterSpotsAlongRailway` 行为变化 | C 批次**只增字段不删字段**；保留 `category`/`visibility`/`maxDistKm` 原值，确保 v2 语义不变 |
| 回滚 | — | `scenic-spots.json` 由 `scripts/build-scenic-spots-curated.mjs` 生成，回滚只需 revert 该文件的 commit；运行时另有 mtime 热加载缓存，重启 API 即失效 |
