## 一、这一轮的口径变更（最重要的一条）

**「尚未覆盖」不再指「没有路线的省」，而是指「未覆盖的地级市」。**

前几轮（阶段 1A / 阶段 2 / 阶段 3 / 薄弱省补强）的选省口径是「哪个省路线条数少」，
本轮改成 `scripts/roadbook-coverage.mjs` 输出的 **todo 地级清单**：
既没有以它为主入口（covered），也没有被任何路线途经（partial）——这些才是库里的真实空白。

由此带来的两个新规则：

1. **`cities` 里可以有「部分覆盖」的地级**。一条路线经过 5 个地级、只有 1 个是 anchorCity 时，
   其余 4 个记为 partial，覆盖率因此上升。
2. **`anchorCity` 只能有一个**。所以「一条路线同时把 A、B 两个地级都变成 covered」做不到 ——
   想要两个 covered，需要两条路线，或把 anchorCity 放在另一个地级上（会让原 anchor 掉回 partial）。
   写稿时不要为了刷 covered 而硬改 anchorCity。

## 三、本轮固化的产线（每一步都有脚本，不靠手感）

一条路线从选题到落库 6 步，全部离线可复算：

1. **选题**：`node scripts/roadbook-coverage.mjs --prov=省` → 该省条数、covered/partial/todo 清单、覆盖率、
   号段台账。优先级 = 条数少 → 覆盖率低 → 缺口多。
2. **坐标与等级核验**：`node scripts/roadbook-poi.mjs <省> <关键词>` → 从
   `data/roads/roadside-spots.json`（36893 条）+ `data/presets/scenic-spots.json`（811 条）
   + `data/roads/places-admin.json`（3564 个行政中心）取**已核验**点位。
   命中不了就不写坐标，改走 `segment.via`。
3. **编号合法性**：`node scripts/roadbook-lookup.mjs check <编号>`（子命令 `poi/place/roads/check/cities/rank`）。
4. **里程实算**：`pnpm.cmd roadbook:measure tmp/m-x.json tmp/m-x-out.json`（= `scripts/roadbook-measure.mts`，
   在 `data/roads/china-road-topo.bin` 上跑 A*）。**取值规则与「里程口径说明」见写作规范 §五**。
5. **写稿**：一次一条，**先写 `tmp/route-x.json`，再用 Python/Node 合并进目标文件**
   （合并脚本做「同 id 覆盖、不同 id 追加」，重复执行不会产生双份路线）。
6. **验收三件套**（顺序不限都要跑）：
   - `node scripts/roadbook-selfcheck.mjs <新文件…>` —— 单文件自检（最快的反馈回路）；
   - `pnpm.cmd roadbook:check` —— 全库判据 A~G + shared V1~V19；
   - `node scripts/roadbook-scan-garbage.mjs <文件>` + `node scripts/roadbook-scan-content.mjs <文件>`。

**单日里程上限**：L1/L2 ≤300km、L3/L5 ≤250km、L4 ≤150km。

## 四、本轮踩到的坑（下一批必须照做）

1. **`scripts/roadbook-measure.mts` 的 haversine 曾经把经度当纬度**（2026-10-22 由我引入、当天修复）：
   ```js
   const la1 = (a[0] * Math.PI) / 180;   // 错：a[0] 是经度
   const la2 = (b[0] * Math.PI) / 180;   // 错：应为 a[1] / b[1]（纬度）
   ```
   后果：**只影响 `straightKm` 与 `ratio`，不影响 `km`（A* 实算结果）**。
   但 `ratio` 是「实算 vs 推算」的判据 —— 东西向跨度大的段 ratio 被严重压低
   （西安→咸阳真实直线 21.1km 被算成 8.3km，比值报 3.18 而真实只有 1.25），
   会把本该「直接采用实算值」的段误判成「必须推算」，**导致里程系统性偏低**。
   **已修复**（改为 `a[1]`/`b[1]`，并加注释）。本轮陕西、湖北两个写稿者各自独立发现了这个 bug，
   并且都**自己重算了正确比值**才套用 1.6 判据 —— 所以本轮 45 条的里程口径是可信的。
   **下一批直接用脚本给的 `ratio` 即可，但要先确认脚本里那两行没被改回去。**
2. **`sources[].url` 不是禁区**（纠正上一批的误传）：`TravelSourceRef.url?` 是 schema 允许的可选字段，
   带上**不会**被 `roadbook-scan-garbage.mjs` 判为杂字。
   库内 `xinjiang-altay-loop.json` 与本轮 `segments-hubei-1.json` 都带了真实官方链接。
   **口径：确实访问并核实过该页面的就写 url，没核实过的不要写。**
3. **`sources[]` 的发布方必须能指到**：「OTA 平台公开线路与自媒体攻略」「官方渠道」这类泛指不够，
   要写清是哪个省市文旅局、哪个景区官网、哪个 OTA 平台。
4. **写完必须亲自回读磁盘复核 POI**：把每个 POI 的「名称 + 经纬度 + 归属城市」逐个回查已核验库。
   本轮抓出过一次专名改写（「宝塔山景区-延安摩崖石刻」被写成「延安摩崖石刻」）。
   **专名一律从库里逐字复制，不要凭记忆重打。**
5. **`anchorCity` 只能有一个**，不要为了刷 covered 把它从 A 改到 B（见 §一）。
6. **县级市/代管县的 `city` 要写地级名**：当阳（宜昌代管）、子长（县级市）等的 `nodes[].city`
   必须落在 `_regions.json` 的地级名单里，否则判据 E 直接拦下。
7. **注意同名的山**：商洛老君山 ≠ 河南栾川老君山；采石矶（马鞍山）与李白墓（当涂）是两处；
   武当山有多个分景区。写之前先确认是哪个。
8. **写稿 agent 可能越界改既有文件**：本轮有写稿者给 4 个既有文件补了缺失的 `roadRefs`
   （`toTravelSummary` 直接取 `r.roadRefs` 且无兜底，缺失时列表页拿到 `undefined`）。
   这个补法**内容正确**（12 个 G 编号全部在 `data/roads/index/` 在册，已逐个核过），
   故予以保留，但**下一批要明确约束「只新建文件，不改既有文件」**。

## 五、内容三渠道怎么落到字段里

| 渠道 | 用来定什么 | 写在哪 |
|---|---|---|
| OTA（携程/飞猪/同程/去哪儿）成熟跟团/自由行线 | 天数结构、停留顺序、住宿落点、是否值得单列一地 | `sources[].usedFor` = 「X 日结构与景区换乘、住宿落点顺序」 |
| 小红书与各类自媒体攻略 | 美食具体到菜名、排队与限流体验、拍摄时段、避坑 | `practical.foodNote` / `bookingNote` / `plan[].tips` |
| 文旅公众号与官网、文物与水利部门公告 | 等级与名录、预约与限流规则、汛期与封山公告 | `pois[].ticketNote` / `intro.seasonNotes` / `practical.warnings` |

`sources` 只写**能指到发布方**的条目，不写「网友说」。查不到出处的说法（热度、荣誉、「最」「第一」）一律不进数据。

### 「预算」怎么写（schema 无 budget 字段 + 红线 R1 不写金额）

- `practical.lodgingNote`：住宿落点 + 档位差异（「县城比景区门口宽松、代价是多开几十公里山路」）；
- `practical.bookingNote`：哪些项目另行收费（门票 / 索道 / 电梯 / 游船 / 观光车 / 讲解分批次）、哪两个时段最贵最挤；
- `pois[].ticketNote`：逐个说明「分别计费 / 预约 / 限流 / 停航封闭」，让读者知道钱花在哪几处；
- `practical.fuelNote`：加油与快充的密度差异、新能源需要回城补能的段落。

**不要为了显得详实而写估价。**

## 七、百度地图 API 的接入现状（2026-10-22 诊断）

**结论：客户端已经接好，AK 的 IP 白名单没放行本机出口 IP，所以当前调不通。**

诊断过程（可复算）：

1. 两把 AK 都返回 `status 210「APP IP校验失败」`（Place / Geocoding / Direction 三个服务端接口全挂）。
2. 探明**本机出口公网 IP 会变**：`120.236.177.39`（ipinfo / icanhazip）与 `120.85.135.41`
   （checkip.amazonaws.com）不一致 —— CGNAT 出口池。
3. 进一步定位到**百度的边缘节点**才是判定点：`api.map.baidu.com` 解析出 4 个 A 记录
   （`14.215.182.208/.24/.56/.113`），直连其中 `.208` 与 `.24` 能拿到 `status 0`，
   直连 `.56` 与 `.113` 就是 210。**同一把 AK 因命中不同边缘而时通时不通**。
4. 连续探测 1596 次后白名单窗口再次关闭（`APP不存在，AK有误`），说明这把 AK 的白名单
   只放行过某一个具体出口 IP。

已交付的工程改动（**key 只从环境变量或 gitignore 的本地文件读，绝不硬编码进业务代码**）：

| 文件 | 改动 |
|---|---|
| `scripts/baidu-geo.mjs` | 重写：AK 只读 `BAIDU_MAP_KEY` 环境变量（回退到 gitignore 的 `tmp/baidu-key.txt`）；新增边缘解析 + 边缘轮换 + 退避重试 + 磁盘缓存；新增 `health` 子命令逐服务探活并区分「IP 未放行」/「服务未开通」/「配额」三类失败；失败时打印可执行的修复步骤与本机出口 IP |
| `apps/api/src/services/roadRouting.ts` | `PlanRouteInput.engine` 增加 `'baidu'` 档（跳过本地拓扑、直接走百度驾车规划）；`baiduDriveRoute` 原本就读 `process.env.BAIDU_MAP_KEY`，本轮之前已存在（2026-10-18 加的） |
| `apps/api/src/services/roadIndex.ts` | `baiduGeocode` 原本就读 `process.env.BAIDU_MAP_KEY`（2026-10-18 加的），本轮未改 |
| `scripts/roadbook-measure.mts` | 新增 `--engine=auto\|baidu\|local`；`auto` = **百度优先 → 本地拓扑 → OSRM → 高德**，百度失败自动回退并在输出里标 `baidu-fallback-local`，让 `mileageNote` 能如实交代口径 |

**怎么修**：登录百度地图开放平台 → 该应用 → 服务设置 → **服务 IP 白名单**，加入
`node scripts/baidu-geo.mjs health` 打印的本机出口 IP；或换一把不做 IP 限制的 AK，
通过环境变量 `BAIDU_MAP_KEY` 提供（**不要写进仓库**）。

**本轮路书里程为什么没有用百度口径**：白名单未放行，实测 1596 次 0 命中。
本轮 45 条的里程走的是**本地国家公路网拓扑 A* 实算**（与既有 179 条同一口径），
**百度一旦放行即可用 `--engine=baidu` 复算并做交叉校验** —— 工具链已经就位。
