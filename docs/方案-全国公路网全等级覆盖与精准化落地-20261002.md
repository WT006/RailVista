## 〇、一页纸

### 0.1 现状：不是"覆盖率低"，是**范式错**

| 等级 | 在册（有编号） | 有几何 | 几何可用性 | 结论 |
|---|---:|---:|---|---|
| 国家高速 | 278 | **0** | — | 一条都没有 |
| 普通国道 | 301 | **33** | 多数偏差 >25%，points/segments 空间不相交 | 只有 11%，且质量不可用 |
| 省道 | 12（占位） | 0 | — | 名录与几何都没有 |
| 县道 X | **0** | 0 | — | 不存在 |
| 乡道 Y | **0** | 0 | — | 不存在 |
| 村道 C | **0** | 0 | — | 不存在 |

连带后果（实测）：

- **拓扑碎裂**：RVRT 40,448 节点 / 44,710 边，**1,237 个连通分量**，主分量只有 17,919 节点（17.2%），bbox 仅 `lng[84.8,109.1] / lat[25.3,40.3]`（青藏东部）。华东/华南/华北全在主分量之外。
- **任意 OD 不可用**：1,406 组测试，本地 A* 成功率 **0.8%**，99% 降级为"两点直线"。
- **单条公路不可信**：G318 声明"上海→聂拉木 5476km"，实际落盘主链是"西藏林芝→四川甘孜 1954km"；33 条几何的端点标注**全部不可信**。
- **里程虚高**：G104 实测 4433.6km vs 官方 2420km（+83%），因为 `points` 与 55 个 `segments` 是两套**互不相交**的坐标集，里程却被相加。
- **前端画不出**：首页"全国公路网"是构建期生成的静态 SVG（`apps/web/src/data/driveRoadNetwork.ts`，153KB 懒加载块），**只画 33 条线**。全等级路网是 10⁷ 量级要素，这个范式天花板就是 33 条。

### 0.2 根因（三条，缺一不可）

1. **数据获取范式错**：以「编号」为检索键，去 Overpass 一条一条捞 `way["ref"="G318"]`。
   但 OSM 里**绝大多数路段没有 ref 标签** —— 本次实测海南省：53,142 条 highway way 中 **47,694 条（89.7%）无 ref**。
   按编号捞，必然只捞到"碰巧标了编号的那几段"；而 3,000+ 条省道意味着 3,000+ 次网络往返，Overpass 只有 **2 个并发槽**（实测 rate limit: 2），这条路走不通。
2. **几何装配算法错**：用"端点最近邻贪心 + 5km 容差拼链"。结果主链是**碰巧串起来的**（G318 的主链在西藏），
   其余段被塞进 segments 且与主链空间不相交、顺序打乱。正确做法是**基于 OSM 共享节点的真实拓扑**做连通分量 + 路径装配。
3. **存储与渲染范式错**：几何按"条"存 JSON（单条最大 600KB）、前端把全部线打包成静态折线。
   全等级路网的正确形态是**要素库（二进制分省）+ 拓扑（CSR）+ 矢量瓦片（MVT）**三层。

### 0.3 方案一句话

> **把"按编号去 OSM 捞线"换成"一次拿全国 OSM 提取物（PBF），在本地建一张全等级路网，再从这张网里派生一切"。**

```
一次下载 33 省 PBF（1.72 GiB，实测 2.3 MB/s）
   → 本地流式解析成「全等级路网要素库」（省片二进制，含 ref/name/等级/几何）
      → ① 普查：真实有多少条路、多少带编号（一次算清，不再猜）
      → ② 名录：官方 G/E（已有 301+278）+ 从要素库派生 S/X/Y/C 事实名录
      → ③ 几何：按编号装配（连通分量 + 直行优先），G/E 100% 覆盖
      → ④ 拓扑：用 OSM 原始 node id 建图（省片 + 接缝），修复 OD
      → ⑤ 瓦片：离线生成 MVT 金字塔，前端 Canvas 按需渲染（全路网可见）
      → ⑥ 质检：覆盖率/偏差/连通性门禁，进 CI
```

## 一、现状实测盘点（先立证据，再谈方案）

### 1.1 在册 vs 有几何（`data/roads/index/*.json` + `coverage-gap.csv`）

```
国道   301 条在册 · 33 条有几何（11.0%）· 268 条 no-geometry
高速   278 条在册 ·  0 条有几何（ 0.0%）
省道    12 条在册 ·  0 条有几何（占位，status=unverified）
县/乡/村道 0 条
合计   591 条在册 · 33 条有几何（5.6%）
```

### 1.2 已有 33 条几何的质量（`data/roads/coverage-gap.csv` 头部）

```csv
key,ref,officialKm,measuredKm,deviation,status,segmentCount,gapCount
G101,G101,909,,,no-geometry,0,0
G104,G104,2420,4433.6,83,broken,55,54
G105,G105,2285,4105.5,80,broken,60,59
```

三类系统性缺陷（来自 `docs/自驾板块-问题诊断与优化方案-20261002.md` §B2 的实测）：

1. **端点假标注 33/33**：用权威名录的 fromPlace/toPlace 直接写进几何，不校验。G318 的 points[0] 在西藏山南（91.34°E），"上海"距其 6709km。
2. **points 与 segments 空间不相交**：G318 主链 4673 点中 **0 点**出现在 71 个 segments 里；G219 是 1/3891；G109 是 1/1539。
3. **segments 顺序打乱**：33/33 文件满足 `segBad = 段数-1`（每段与下一段都不相接），无法靠"重排"修复，只能重建。

### 1.3 拓扑与规划（`china-road-topo.meta.json`，v0.5.3 实测）

```
节点 40,448 · 边 44,710 · 连通分量 1,237 · 主分量 17,919 节点（17.2%）
主分量 bbox：lng[84.8,109.1] / lat[25.3,40.3]（青藏东部）
OD 测试 1,406 组 → 本地 A* 成功率 0.8%，99% 降级 direct（两点直线）
```

**碎裂的机制性原因**（这一点决定了 M4 的做法）：`build-road-topology.mjs` 用
「坐标量化到 1e-5 度 + 1km 跨线边」来近似连图。但 OSM 里两条 way 的共享节点是**同一个 node id**，
用坐标近似会因为浮点/简化误差把同一个物理节点算成两个；而 1km 跨线边又会把不相关的路强行连上。
**正确做法是直接用 OSM 原始 node id 建图** —— 共享节点自动合并，连通性由真实拓扑决定。

### 1.4 前端渲染范式

```
apps/web/src/data/driveRoadNetwork.ts   153KB（33 条线，构建期生成的扁平坐标流）
apps/web/src/data/driveBackdrop.ts      170KB（含 1035 个景点热力点）
叠加方式：SVG <path>，viewBox 1000×971
```

问题不在"丑"，在于**这个范式无法长大**：33 条 = 153KB，全国 G/S/X 约 3.5 万条 → 约 160MB；
再加乡道村道（10⁶~10⁷ 条）已无意义。**必须换成瓦片金字塔 + 视口裁剪。**

### 1.5 三条根因与对应解法（本文档的骨架）

| 根因 | 现做法 | 新做法 | 章节 |
|---|---|---|---|
| 数据获取 | 按编号查 Overpass（一条一线） | 分省 PBF 全量下载 + 流式解析 | §三、§五 P1/P2 |
| 几何装配 | 端点贪心 + 容差拼链 | 共享节点连通分量 + 直行优先路径装配 | §五 P4 |
| 存储渲染 | 单条 JSON + 静态 SVG | 省片二进制 + CSR 拓扑 + MVT 瓦片 | §四、§五 P5/P6 |

## 二、目标定义：什么叫"全覆盖 + 精准化落地"

需求原话是"**所有的道路精准化落地，所有路网搭建**"。这句话必须先拆成可验收的三层，否则永远做不完也验收不了。

### 2.1 三层覆盖定义

| 层 | 定义 | 目标 | 验收口径 |
|---|---|---|---|
| **T1 物理路网层** | 全国所有可通行的道路几何（含无编号路段） | **OSM 全量 100% 入库** | `build-road-ways.mjs` 覆盖全部 33 省；census.json 中 highway way 数 = PBF 中数量（可复核） |
| **T2 编号实体层** | 有编号、可"整条查看/整条沿程"的公路实体 | 高速 278/278、国道 301/301 = **100%**；省道 ≥ **90%** 的 ref 值可成链；县道 ≥ **80%**；乡道/村道**不承诺编号完整** | coverage-gap.csv：G/E 的 hasGeom = 100%，一级 status ≠ no-geometry |
| **T3 拓扑可通行层** | 能规划任意 OD 的图 | 省内 OD 成功率 **100%**，跨省 ≥ **95%** | `scripts/eval-od.mjs`：抽样 1,000 组 OD，engine != direct 比例 ≥95% |

### 2.2 精度分级（"精准化"的可验收定义）

"精准"不是形容词，是**可度量的分级**。每一级都进 `RoadIndexEntry.precision` 字段并在 UI 出徽标：

| 级 | 判据 | UI 允许说什么 | 允许用来做什么 |
|---|---|---|---|
| **A** | OSM 几何 + 官方里程，偏差 **≤10%**；端点落在声明起终点 20km 内 | "走向已核对" | 里程、章节、桩号、沿程推送、路书 |
| **B** | 仅 OSM，官方里程偏差 **10%~25%** | "走向为 OSM 还原（估算）" | 画线、沿程匹配；里程标"约" |
| **C** | 无编号或仅拓扑连通（偏差不可判） | "路网连通层，无编号信息" | 底图渲染、路径规划；**不出现在"按编号查询"结果里** |
| **X** | 偏差 >25% 或几何自相交/跳点 | **不发布**，只进质检报告 | 无 |

**门禁**：`verify-road-network.mjs` 中，G/E 的 A+B 级合计必须 ≥95%，否则构建失败（阻断发布）。

### 2.3 对外口径（诚实边界，必须写进 UI 与文档）

可以说：

- "已收录国道 301 条、国家高速 278 条**全线走向**"
- "省道 XXXX 条可查，县道 XXXX 条可查"
- "路网数据来自 OpenStreetMap（众包），里程为估算值，不作为导航依据"

不可以说（今天在说，必须改）：

- ❌ "全国公路网"（当只有 33 条线时）→ 改为"已收录几何 33 / 591 条"
- ❌ "县道 20~40%、乡道村道 <10%（仅名称）" → 实测是 **0 条**，v0.5.3 已修为如实披露

### 2.4 不可达边界（必须提前讲清，避免后期返工）

1. **村道"编号"不存在全国公开名录**：村道 C### 由县级人民政府确定，全国 270 万公里、约 10⁵~10⁶ 条，
   无统一登记公开渠道。全国普查实测：OSM 中 `ref=C###` 只有 **1,291 条 way / 379 个编号值**（海南为 0），
   相比 270 万公里的体量等于没有。
   → 我们能做的是：**村道的物理几何 100% 入网（T1/T3），编号实体按可用 ref 尽力而为（T2 不承诺）**。
2. **县道/乡道编号在 OSM 中覆盖率不均**：X 有 675 条 way（海南），Y 只有 92 条。
   → 省道靠"官方名录 + OSM ref"双源；县道靠"OSM ref 派生 + 名称兜底"；乡道/村道靠**网络层**。
3. **OSM 不是测绘成果**：几何精度米级~十米级不等，山区/新建路段可能缺失或错位。
   → 用"官方里程比对 + 里程碑桩号抽查"做精度分级，而不是宣称"精准"。

## 三、数据源决策（含本次实测）

### 3.1 主源：OSM 分省 PBF 提取物（**决定性的改变**）

```
https://download.openstreetmap.fr/extracts/asia/china/{province}-latest.osm.pbf
```

实测（2026-10-02）：

| 项 | 结果 |
|---|---|
| 可达性 | **33 省全部 200 OK**（Geofabrik / planet.openstreetmap.org 在本机网络 10s 超时失败，**不可用**） |
| 省列表 | anhui, beijing, chongqing, fujian, gansu, guangdong, guangxi, guizhou, hainan, hebei, heilongjiang, henan, hubei, hunan, inner_mongolia, jiangsu, jiangxi, jilin, liaoning, macau, ningxia, qinghai, shaanxi, shandong, shanghai, shanxi, sichuan, tianjin, tibet, xinjiang, yunnan, zhejiang, hong_kong |
| 体积 | 合计 **1.72 GiB**；最大 guangdong 184MB，最小 macau 3.5MB |
| 速度 | **2.34 MB/s** → 全国约 13 分钟；单省 4s~80s |
| 版本 | 每日更新（last-modified: 2026-10-01），附带 {prov}.state.txt（sequenceNumber，可做增量判断） |
| 备源 | `ftpmirror.your.org`（实测可达）；Geofabrik（本机不通，用户其他网络环境可能可用）；BBBike 定制提取（239 城市，无中国全境） |

**为什么这一步是决定性的**：

- 一次拿到**全部**要素（含无 ref 的乡道村道），不再受"编号"限制；
- 零网络往返地派生一切（几何/索引/拓扑/瓦片），可重复、可断点、可增量；
- Overpass 退居"补漏 + POI"角色，不再承担主数据生产（实测其 rate limit 只有 2 个并发槽）。

### 3.2 为什么必须放弃"按 ref 抓 Overpass"

| 问题 | 证据 |
|---|---|
| 无 ref 的路捞不到 | 海南 53,142 条 highway way 中 **89.7% 无 ref** |
| 请求数 O(N) | 省道 3,000+ 条 = 3,000+ 次请求；每次 30~180s，全量需数天且随时限流 |
| 限流真实存在 | `overpass-api.de/api/status`：`Rate limit: 2, 1 slots available`；历史记录中连续 15 条即出现整端点 504 |
| 端点拼链必然错 | 无 ref 的断口无法用"距离"判断是否同一编号，贪心必然串错（G318 即典型案例） |
| 城市过境段缺失 | 城区路段 ref 常挂在别的路上或不标，导致"东一段西一段" |

> 结论：Overpass 保留，但只做三件事：① PBF 缺失要素的补漏；② POI/服务区/观景台抓取；③ 单点验证。

### 3.3 辅助源与用途边界

| 源 | 用途 | 不用于 | 备注 |
|---|---|---|---|
| 《国家公路网规划》2022 附表 | G 301 / E 278 权威编号 + 起讫点 + 控制点 | 几何 | 已有 `authoritative/plan-2022-*.json` |
| 各省《省道网规划》公示 | 省道编号 + 起讫点（人工核对首期 6 省） | 几何 | 需人工，属内容工作量 |
| 交通运输部统计公报 | 各等级**里程总量**（校验用） | 逐条 | 2024：国道 29.9万 / 省道 41.01万 / 县道 69.88万 / 乡道 124.34万 / 村道 270.14万 km |

### 4.3 主键与命名规范（硬编码成校验，进库前跑）

```
G + 1~3 位（≥100）  → 普通国道，全国唯一        主键 G318
G + 1~2 位（<100）  → 国家高速主线              主键 G4
G + 4 位            → 国家高速                  主键 G5611
G + 1~2 位 + W/E/N  → 高速并行线                主键 G15W
S + 1~4 位          → 省道，省内唯一            主键 {省}:S101
X + 1~4 位          → 县道，省内唯一            主键 {省}:X342
Y + 1~4 位          → 乡道，县级唯一            主键 {省}:{县}:Y012
C + 1~4 位          → 村道，县级唯一            主键 {省}:{县}:C003
无编号              → 不建实体，只进网络层      net:{prov}:{wayId}
```

**ref 清洗规则**（在 ② 里做，写单测）：

- 多编号共线：`G318;G214` → 两边都算（几何允许重复出现，符合现实）
- 大小写/空格：`g318`、`G 318` → 归一化
- 纯数字 ref（如 `26`）：进 unknown-num 桶，**不自动入库**（人工规则后再开）
- 非法/超长 ref：丢弃并计数（进普查报告，不静默丢）

### 4.4 中间格式规格：RVWN（Road Way Network，省片二进制）

```
Header (32B)
  magic      char[4]  'RVWN'
  version    u16      1
  provId     u8       省代码
  reserved   u8
  wayCount   u32
  nodeCount  u32
  strCount   u32
  flags      u32      bit0=含 track, bit1=含 service, ...
StringPool
  strOffsets u32[strCount+1]   相对 blob 起点的偏移
  blob       UTF-8 去重字符串（ref / name / highway 取值）
Ways (wayCount × 32B)
  id         u64      OSM way id
  strId      u32      指向 StringPool 的三元组索引
  cls        u8       E/G/S/X/Y/C/other
  flag       u8       bit0=oneway bit1=bridge bit2=tunnel bit3=toll
  nodeOff    u32      在 WayNodes 中的 u32 序号偏移
  nodeCnt    u16
  lenM       u32      折线长度（米，抽取时顺带算好）
WayNodes
  u32 delta-varint 序列（复用 OSM 原始 node id，跨省天然唯一）
Nodes (nodeCount × 24B，按 id 升序)
  id         u64      OSM node id
  lng        f64
  lat        f64
```

**为什么用 OSM node id 而不是坐标**：
① 省界/跨省路段天然对齐，省片可直接拼接；② 拓扑建图不需要任何容差参数；③ 增量更新时按 way id 做 diff 即可。

### P2 · 全等级要素库（2.5 人日）

**文件**

```
scripts/build-road-ways.mjs    PBF → data/roads/net/{prov}.rvwn（规格见 §4.4）
scripts/lib/rvwn.mjs           读写 RVWN（writeRvwn / readRvwnHeader / iterateWays / lookupNode）
```

**算法**

1. Pass A：流式读 ways，命中 highway 白名单的写入临时数组 + 记录所需 node id（Uint32Array 增长池）。
   - 白名单：motorway,trunk,primary,secondary,tertiary,unclassified,residential,living_street,service,road,track + 对应 _link
   - 可配置：--with-track（默认含，村道/机耕道）、--with-service（默认含，园区/景区内部路）
2. node id 集合排序去重 → Pass B：流式读 nodes，只保留在集合内的坐标（按 id 升序写入）。
3. 合并：ways + wayNodes + nodes → {prov}.rvwn；顺带算每条 way 的长度、bbox、所属省。
4. 空间二次分片（大省）：若单省 node 数 > 800 万，按 1° 纬度带切 {prov}-{band}.rvwn。

**规模实测**（全国 31 省普查）：highway way **9,101,780** 条，way 点引用 **287,816,026** 个（平均 31.6 点/way）。
按 24B/节点估算，全国唯一节点约 1.2~1.5 亿（约 3~3.6GB 坐标数据），**不能整体入内存** —— 必须分省。

**内存预算**：广东（最大省，1,014,238 条 highway way，约 3,200 万点引用）去重后节点约 1,500 万 × 24B ≈ 360MB，
单省可控；峰值内存由"单省 + 排序缓冲"决定，**<1.5GB**。若某省超 800 万节点，按 1° 纬度带二次分片。

### P4 · 几何装配（3.5 人日）★ 里程碑 M2 的核心

**文件**

```
scripts/lib/road-assemble.mjs    装配算法（纯函数，可单测）
  - unionFindComponents(ways)            → 连通分量
  - traceComponent(ways, nodeAdj)        → 有序折线（直行优先）
  - assembleRef(ref, ways, nodes)        → { points, components[], nodes[], stats }
scripts/build-road-geom.mjs      遍历名录 → 装配 → 写 geom/{key}.json
```

**算法（替换 chainWays 的贪心，这是本方案的技术核心）**

```
输入：某 key 的全部 way（跨省，从 net 分片按 ref 索引取）
1. 建节点邻接：node id → [(wayId, 在 way 中的位置)]
2. 并查集求连通分量（以共享 node id 为边）
3. 每个分量内：
   a. 计算每个节点的度（连接了几条 way）
   b. 端点集 = 度为 1 的节点；若无（闭环），任取一点
   c. 从端点出发，走未使用的 way；遇到度 ≥3 的交叉点时：
      选择"与当前行进方向夹角最小"的 way（直行优先），避免在路口拐进支线
   d. 结束条件：无可用 way，或回到起点（闭环）
4. 输出 components[]（每个分量一条有序折线），按长度降序
5. points = components[0]（最长分量）；segments = components[1..]（其余分量）
   —— 语义纠正：segments 不再是"丢弃的孤儿"，而是"该编号的其它连通分量"
6. 端点命名：用分量首/末点 20km 内最近的地名锚点（places-geo.json）
   —— 不再无条件采用名录的 fromPlace/toPlace
7. 里程：componentKm[]；entry.lengthKm = Σ componentKm（"已收录里程"）
8. 与官方里程比对 → precision 分级（§2.2）
```

**为什么这个算法能修复 G318**：
G318 在 OSM 里带 ref 的 way 会形成若干**真实存在的连通分量**（上海—武汉、武汉—重庆、成都—拉萨…），
每个分量的点都在正确的地理位置。旧算法把这些分量用 5km 容差硬拼成一条"主链"，
拼不上就丢进 segments —— 于是主链成了西藏那一段、"上海"被贴在了错的端点上。
新算法**不拼**：如实输出 N 个分量 + N-1 个断点说明，UI 显示"已贯通 XXXX km（共 N 段，最大断口 XX km）"。

**断口修补（可选，P4 后置）**：对每个断口做局部 Overpass around:2000 查询找无名连接段，
只补"几何上确实连通"的，补不上就如实标注（沿用 fetchConnectingWaysAround 的城市区域跳过逻辑）。

## 附录 C · 术语表

| 术语 | 含义 |
|---|---|
| **PBF** | OpenStreetMap 的二进制交换格式（Protocolbuffer Binary Format），含全量节点/道路/关系 |
| **RVWN** | 本方案定义的"省片全等级路网要素库"二进制格式（§4.4） |
| **RVRT** | 现有公路拓扑二进制格式（magic 'RVRT'，CSR 布局，与铁路 RVTP 同构） |
| **MVT** | Mapbox Vector Tile，矢量瓦片格式（protobuf），本方案用于前端全路网渲染 |
| **连通分量** | 通过共享 OSM node id 相连的一组 way；一个编号可能有多段（未贯通） |
| **直行优先** | 在度数 ≥3 的交叉节点处，选择与来向夹角最小的 way，避免误入支线 |
| **事实名录** | 从要素库派生的编号清单（区别于官方发布的名录） |
| **T1/T2/T3** | 物理路网层 / 编号实体层 / 拓扑可通行层（§2.1） |
| **A/B/C/X 级** | 精度分级（§2.2） |

### D.5 已知边界（如实标注，未解决）

1. **国道/高速联络线**：44 条国道联络线 + 部分高速联络线在 OSM 中尚无该编号的路段（规划在册、现实未标志）；
2. **官方里程元数据**：权威名录仅 136 条有官方里程，其余无法比对（标 C）——这是"里程精度看起来不高"的主要原因，不是几何问题；
3. **城区断档**：一条长线在 OSM 中常被拆成上百个连通分量（G318 114 段），已按 ≤1.5km 紧公差接续（G318 缝合 148 处），剩余断口如实展示；
4. **无编号路网**：乡道/村道的物理几何已全部进入位图背景与拓扑，但"编号实体"只能覆盖 OSM 中确有 ref 的部分（村道全国仅 478 条）；
5. **沙箱限制**：本机 DSH 沙箱下 vite/tsx 的 dev server 会因 esbuild 管道 stdio 报 \`spawn EPERM\`；
   构建（\`pnpm build\`）与三视口探针需在放宽权限下执行（本次已在放宽权限下实测通过）。
