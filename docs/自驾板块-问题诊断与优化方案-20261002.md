# 自驾板块（万里路书）问题诊断与优化方案

- **日期**：2026-10-02
- **诊断基线**：`heyworldchannel-20261002` @ `a94c849`（v0.5.2）
- **范围**：`apps/web/src/pages/Drive*.vue`、`apps/web/src/components/Drive*.vue`、`apps/api/src/routes/drive.ts`、`apps/api/src/services/road*.ts`、`packages/shared/src/drive/*`、`data/roads/*`
- **方法**：通读源码 + 全量数据文件实测统计 + 用仓库已编译的 `packages/shared/dist` 实跑真实匹配器 + 解析 `china-road-topo.bin` CSR 二进制复现 snap/A*
- **说明**：本报告只做诊断与方案，不含代码改动。所有结论均标注 `file:line`；标注「实测」的为脚本统计结果；标注「推测」的为尚未验证的假设。

## 摘要：先说结论

自驾板块当前的问题**不是 UI 细节问题，而是「数据可信度」问题伪装成了 UI 问题**。

三条主线：

1. **大量功能其实已经在代码里，但被自己的时序/数据缺陷废掉了**。沿程景点列表写了 `opacity: 0` 的滚动揭示动画，而揭示器在数据到达前就抓空了元素 —— 景点**存在但永远不可见**。这不是设计问题，是一个 `onMounted` 时序 bug。
2. **公路几何数据本身是错的**，不是渲染错。G318 声明「上海→聂拉木 5476km」，实际落盘可渲染的主链是西藏—四川西部一段 1954km，且与另外 71 段孤链**坐标完全不相交**。全国 33 条有几何的公路里，**11 万公里已抓取、已落盘的数据永远不会被渲染**。用户看到的「G318 景点混乱」是数据问题，改 UI 改不好。
3. **「全国公路网」只画了 33 / 591 条（5.6%）**，但首屏文案写的是「全国公路网示意图」。高速 278 条几何覆盖 **0%**，县道/乡道/村道**一条都没有**。

因此建议的优先级顺序是：**先修 4 个 P0（其中 2 个是纯代码 bug，当天可上线）→ 再修数据可信度 → 最后做视觉统一**。视觉重做放在最后，因为现在重做等于把错误数据画得更漂亮。

## 一、逻辑与信息架构

### A1【P0】沿程景点列表存在但永远不可见

**现象**：进入 `/drive/trip` 后，路线卡、地图、章节条都正常渲染，但右栏「沿途景点」区域一片空白。控制台无报错，API 返回也正常。

**影响**：自驾板块**最核心的卖点功能完全不可见**。用户看到的是「一条线 + 什么都没有」。

**根因**（时序 bug，非设计）：

1. `DriveTrip.vue:26` 在 setup 阶段调用 `useScrollReveal('.drive-scroll-reveal')`。
2. `useScrollReveal.ts:18-22` 在 `onMounted` 里 `document.querySelectorAll(selector)`，若 `!elements.length` 则 **直接 return，不再注册 IntersectionObserver**。
3. 但 `DriveTrip.vue:99` 的 `onMounted(load)` 是**异步**的，`load()` 要等 `await api.getDriveAlong(...)`（`DriveTrip.vue:80`）才结束。模板在 `loading=true` 时走 `v-if` 分支（`:287`），只渲染骨架屏 —— **`.drive-spot` 元素一个都不存在**。
4. 结果：`querySelectorAll` 返回空 → 提前 return → IntersectionObserver **从未注册**。
5. 而 `drive.css:1707-1711` 的初始态是：
   ```css
   .drive-scroll-reveal { opacity: 0; transform: translateY(8px); }
   .drive-scroll-reveal.is-revealed { opacity: 1; transform: none; }
   ```
   `is-revealed` 永远不会加上 → **所有景点卡片永久 `opacity: 0`**。

**验证**：已确认 `DriveTrip.vue:428` 的景点卡片确实带 `class="drive-spot drive-scroll-reveal"`，且全仓仅此一处使用该类（`DriveRoad.vue` 未调用 `useScrollReveal`）。

**方案**：
- 改 `useScrollReveal` 为 **MutationObserver 驱动**或提供显式 `reveal(selector)` 重扫接口，在 `load()` 的 `finally` 里调用；
- 或最小改动：把 `opacity: 0` 的初始态改为 `@media (prefers-reduced-motion: no-preference)` 之外不加，或给 `.drive-scroll-reveal` 加 `noscript` 式兜底 —— 但推荐前者，因为骨架屏→内容的动画是想要的效果，只是要让它真的能触发；
- **同时修 `useRoadDraw`**：`useRoadDraw.ts:10-12` 同样是 `onMounted` 一次性取 `pathRef.value`，`DriveTrip.vue:24-25` / `DriveRoad.vue:32-33` 调用时 `ref` 为 null（模板在 `v-else` 分支内）→ **路线描边动画也从不播放**。这是同一个根因的第二处表现，应一起抽成 `watch(pathRef)`。

**工作量**：0.5 人日。**这是全报告投入产出比最高的一项。**

### A2【P0】「设为起点/终点」按钮永远取候选第 1 项

**现象**：在编号键盘选了一条公路（如 G318），候选列表出现 8 条，点了列表里第 5 条，然后点「设为起点」—— 结果起点变成了**列表第 1 条**。

**影响**：公路编号筛选实际上不可用；用户会认为「按钮坏了」。

**根因**（`DriveHome.vue:216-221`）：

```ts
function setRoadAsConstraint(field: 'from' | 'to') {
  const hit = roadCandidates.value[0];   // ← 永远是排序后的第 1 项
  if (!hit) return;
  if (field === 'from') from.value = hit.name;
  else to.value = hit.name;
}
```

按钮渲染在候选列表**下方**（`DriveHome.vue:410-413`），列表有 8 项（`:400` `.slice(0, 8)`），但函数体从不接收用户选中的那一项。候选按编号数字升序（`:182-186`），所以「设为起点」永远设成编号最小的那条。

**方案**：引入 `selectedRoadHit` ref，候选项点击时写入；按钮改为 `setRoadAsConstraint(field, selectedRoadHit.value ?? roadCandidates.value[0])`，并在未选中时禁用或高亮提示。

**工作量**：0.5 人日。

### A3【P0】本地拓扑 `nodeFlag` 读取偏移错误 → 99% 的 OD 规划降级为两点直线

**现象**：任意起点/终点的自驾路线规划，绝大部分结果显示为一条**笔直的线**，不跟随任何道路。引擎提示为「两点直连（干线未覆盖，仅供示意）」。

**影响**：C1 点对点模式在无高德 key / 高德超时的场景下**基本不可用**。而这正是隧道/山区/无信号场景的兜底路径。

**根因**（二进制格式读写不一致）：

- 写入端 `scripts/build-road-topology.mjs:198`：`buf.writeInt32LE(1, 16); // reserved=1：尾部含 nodeFlag`
- 读取端 `apps/api/src/services/roadTopology.ts:111`：`const reserved = buf.readInt32LE(20);`

**实测**：`readInt32LE(16) = 1`、`readInt32LE(20) = 0` → `roadTopology.ts:112` 的 `if (reserved === 1 …)` **恒为 false** → `nodeFlag` 永远为 `null`。

**实测代价**（用真实二进制复现 `nearestRoadNode` + `roadRouteLeg`，38 城全有序 OD 对 1406 组）：

| 指标 | 实测 |
|---|---:|
| snap@5km 失败（需 150km 救援或彻底失败） | 986 / 1406 = **70.1%** |
| snap@150km 仍失败 | 594 / 1406 = 42.2% |
| A* 找到路径 | **14 / 1406 = 1.0%** |
| **合计降级为 `direct`（两点直线）** | **1392 / 1406 = 99.0%** |

成功的 3 条：`格尔木→西宁`(795km)、`格尔木→成都`(2650km)、`西宁→成都`(2401km) —— 都是西北干旱区，恰好是主连通分量覆盖最好的区域。

**更深层根因**：图本身碎裂。连通分量 **1237 个**，最大连通分量仅 **31,300 节点 = 全图 17.2%**，小于 5 节点的小分量有 441 个。上海、杭州、成都、三亚在 5km 容差下 **snap 直接失败**。

已用 `reserved@16` 手动加载 `nodeFlag` 后校验：主分量节点数 = 31,300，与 `china-road-topo.meta.json` 的 `mainCompNodes: 31300` **完全一致** —— **数据是好的，读取端偏移写错了**。

**⚠️ 修复后的实测结果（2026-10-02 已改代码并复测，推翻本报告初版预测）**：

| 指标 | 修复前 | 修复后 |
|---|---:|---:|
| nodeFlag 是否加载 | ✗ null | ✓ 31,300 节点 |
| A* 成功率 | 0.8% | **0.8%（无变化）** |
| 降级 direct | 99.2% | **99.2%（无变化）** |

**本报告初版预测「1% → 30~50%」是错的。** 偏移修复是**必要但不充分**的：它让 snap 逻辑正确（不再选中小分量里的孤立节点），但**瓶颈在图本身碎裂**，修偏移无法弥补。

**真正的瓶颈（实测）**：
- 图 182,007 节点 / 206,609 边，**连通分量 1,237 个**；
- 最大连通分量 31,300 节点 = **全图 17.2%**；前 10 分量累计仅 40.8%；
- <5 节点的小分量 **441 个**；
- **主分量 bbox = lng[84.79, 109.07] / lat[25.32, 40.26]** —— 只覆盖青藏高原东部，**华东、华南、华北全部不在主分量内**；
- meta 里 33 条路（`G104`~`G331`）**各自是独立分量，彼此没有缝合**（`crossLinks: 21917` 只在路内生效）。

**结论**：当前 L2 拓扑**只能做「同一条公路内的区间路径」**，做不了「跨公路跨省 OD」。这不是 bug，是数据建设阶段未完成（对应 N4 阶段）。

**方案**：
1. **已修**（2026-10-02）：`roadTopology.ts:111` 改 `readInt32LE(16)`，并保留 offset 20 的兼容回退分支；`build-road-topology.mjs:198` 加注释锁定偏移约定。**这步必须做，但不宣称它能提升 OD 成功率。**
2. **降级预期、诚实披露**（0.5 人日）：`engineNote` 在 `engine === 'direct'` 时明确写「本地路网仅覆盖青藏部分干线，跨省规划暂不可用」，避免用户把两点直线误认为真实路线。
3. **跨路缝合**（3~5 人日，N4 阶段）：建图阶段按**几何交叉点**（而非仅路内端点）把 33 条路缝合为一张连通图——在两条 way 相交处补 crossLink 边（带换乘惩罚）。这是把 OD 成功率从 1% 提上去的**唯一有效路径**，但工作量与数据抓取量成正比。
4. **兜底优先级**：在缝合完成前，跨省 OD 应**默认走高德在线**（`engine: 'amap'`），本地 A* 仅在青藏范围内启用。

**工作量**：偏移修复 0.5 人日（已完成）；诚实披露 0.5 人日；跨路缝合 3~5 人日（N4）。

### A4【P1】起点/终点无法搜索详细地址，且后端在「骗人」

**现象**：起点/终点输入框只能匹配到城市级地名。输入「浦东新区世纪大道100号」无结果。且后端报错文案提示「直接点地图选点」，但**页面上没有点选功能**。

**影响**：自驾的核心场景是「从家到景区」，家通常不是城市名。地址搜索缺失让 C1 模式实用性大打折扣。用户被错误文案引导到一个不存在的功能。

**根因（三个叠加）**：

1. **前端无显式地址入口**。`DriveHome.vue:95` 调的是无 kind 参数的 `api.suggestDrivePlaces(q, undefined, 8)`，四类混合联想，打分是纯字符串匹配（`roadIndex.ts:107-113`：完全相等 100 / 前缀 80 / 包含 50），**无拼音、无编辑距离、无分词**。`data/roads/places-geo.json` 仅 217 条。
2. **geocode 兜底存在但不可用**。`drive.ts:54-57` 触发 `geocodeFallback` → `amapGeocode`（6s 超时）**串行 await** → `nominatimGeocode`（6s 超时），**最长阻塞 12 秒**。且 `amapGeocode` 的 `level` 恒返回 `'county'`（`roadIndex.ts:233`），未使用高德实际返回的 level。前端 `DriveHome.vue:104` 是空 `catch {}` → 用户表现为「输入了没反应」。
3. **地图点选从未实现**。`drive.ts:178` 的 `badRequest('缺少参数：from+to（点对点）/ road=编号…')` 与 `roadRouting.ts:39` 的 `PlaceNotFoundError('未找到「X」，请换个说法或直接点地图选点')` 都承诺了这个功能，而 `DriveHome.vue:266-284` 的 SVG 只有 `@click` 挂在 `<path>` 上（`:271`，`class="drive-netmap__road"`），**没有任何获取坐标的 handler**。

**方案**：
- **短期**（当天）：把两处错误文案改成诚实提示（去掉「点地图选点」），或直接实现点选 —— 鉴于首页已有全国 SVG，实现成本低，见 V3。
- **中期**：给联想加拼音首字母（`pinyin` 字段入库，参考铁路 `stationIndex.ts` 的 138 行实现）+ 编辑距离容错；
- **中期**：`geocodeFallback` 改为**高德 / Nominatim 并行**（`Promise.any`），超时压到 3s；增加结果缓存（同 query 24h）；
- **中期**：把 217 条 places 扩容 —— 优先从 `data/presets/stations-geo.json`（1324 条）复用，再接 OSM `place` 节点。

**工作量**：文案 0.5 人日；并行 geocode + 缓存 1 人日；拼音 1.5 人日；地点扩容按数据量另计。

### A5【P1】公路编号混入起点/终点输入框，选中后类型信息被丢弃

**现象**：在起点框输入「G318」，联想出「公路」类结果，选中后输入框只剩文本 `G318`，系统无法知道它是公路还是地名。用户分不清「我要走 G318 这条公路全程」和「我要从 G318 某个点出发」。

**影响**：这是自驾板块**最核心的信息架构歧义**。用户看到「点对点」和「整条公路」两个入口，但输入框完全一样，行为完全不同，且没有任何区别提示。

**根因**（`DriveHome.vue`）：

1. **选中时丢弃类型**（`:109-117`）：
   ```ts
   function pickHit(field: 'from' | 'to', hit: PlaceHit) {
     if (field === 'from') { from.value = hit.name; fromOpen.value = false; }
     else { to.value = hit.name; toOpen.value = false; }
   }
   ```
   只写入 `hit.name`，**不保存 `hit.kind` / `hit.id` / `hit.lng` / `hit.lat`**。类型信息在 UI 层就被扔了。
2. **后端只能靠字符串再猜一次**。`roadRouting.ts:57-81` 的 `resolveEndpoint` 顺序是 `parseLngLat` → `resolvePlace`（**先 place 后 road**）→ `geocodeFallback`。`roadIndex.ts:194-205` 明确地名字优先。所以「G318」这种输入若被当地名处理，会走到 geocode 拿到一个无意义坐标。
3. **「点对点」与「整条公路」共用同一套 OD 表单**，但语义完全相反：
   - 点对点：起点/终点是**地理坐标**，产出是一条**规划出来的最优路径**；
   - 整条公路：公路编号是**主键**，产出是**该公路官方走向的全部几何 + 全部沿途景点**。

### A7【P2】起点/终点联想：共享序号互相丢弃 + 无防抖 + 无键盘操作

**现象**：在「起点」输入后立刻在「终点」输入，**起点的下拉永远不会弹出**。

**根因**（`DriveHome.vue:84-107`）：

```ts
let suggestSeq = 0;                    // ← 单个共享序号，不是每字段一个
async function refreshSuggest(field: 'from' | 'to') {
  const seq = ++suggestSeq;
  ...
  if (seq !== suggestSeq) return;     // ← 迟到响应丢弃
```

`seq` 是**全局单计数器**。用户在起点输入（seq=1）后立即在终点输入（seq=2）→ 起点的响应到达时 `1 !== 2` → **被当作迟到响应丢弃**。铁路版是 `fromActive`/`toActive` 分离设计（`SelectTrip.vue:328-336`），自驾没有。

**叠加问题**：
- **无防抖**：`:297` / `:324` 的 `@input="refreshSuggest(...)"` 每次按键直发请求（铁路有 250ms `suggestTimer`，`SelectTrip.vue:312-341`）；
- **无键盘导航**：联想 `<li>` 无 `@keydown`，↑↓/Enter/Esc 全不支持（铁路有 `onSuggestKey`，`SelectTrip.vue:370-387`）→ **联想列表完全无法用键盘操作**，无障碍不达标；
- **无建议框防溢出**：铁路有 `has-suggest-open` 类提升卡片 z-index（`SelectTrip.vue:806`），自驾 grep 0 命中；
- `odBusy`（`DriveHome.vue:83`）**声明后从未被赋值为 true**，只在模板 `:346` 当 `:disabled` 用 → 恒为 false，**「出发」按钮的禁用态是死代码**，提交期间无任何 pending 指示。

**方案**：`suggestSeq` 改为 `{ from: 0, to: 0 }` 双计数器；加 250ms 防抖；把 `onSuggestKey` / `has-suggest-open` 从 `SelectTrip.vue` 抽成共享 composable；`odBusy` 真正接线。

**工作量**：1.5 人日（建议抽成 `useSuggestField` 共享 composable，Web + 鸿蒙复用）。

### B2【P0】G318 几何是错的 —— 声明「上海→聂拉木」，渲染出来在西藏西部

**现象**：用户点开 G318，看到的路线从西藏林芝一带开始，到四川甘孜结束，沿程景点全是鲁朗、卡子拉山、新都桥、泸定桥等西部景点，**完全没有上海/江浙沪/湖北/重庆的影子**。里程显示 1954km（实际 G318 全长 5476km）。

**实测数据**（`data/roads/geom/G318.json`）：

```
nodes    = [{name:"上海",atKm:0}, {name:"聂拉木",atKm:1953.5}]
points[0]    = [91.336, 29.671]   ← 西藏山南，距拉萨 33km
points[last] = [103.461, 30.388]  ← 四川甘孜
points bbox  = lng 91.26~103.58, lat 29.48~30.49
points 数量   = 4673
```

`nodes[0].name = "上海"` 但 `points[0]` 在西藏 —— **端点标注是假的**。`fetch-road-geometry.mjs:230-233` 无条件写入 `fromPlace`/`toPlace`，**不校验是否真的落在几何端点**。上海（121.4°E）只存在于 `segments` 里（seg50/58/59/70 的起点都在 120.6~121.4°E）。

**更严重的系统性问题**（33 条有几何的公路全部如此，实测）：

| key | `points` | `segments` | points 中出现在 segments 里的坐标数 |
|---|---:|---:|---:|
| G318 | 4673 | 71 段 / 7547 点 | **0 / 4673** |
| G219 | 3891 | 62 段 / 20316 点 | **1 / 3891** |
| G109 | 1539 | 58 段 / 4208 点 | **1 / 1539** |
| G315 | 679 | 29 段 / 1694 点 | **1 / 679** |

**所有 33 个文件的 `points` 与 `segments` 是两套互不相交的坐标集**，且 `segments` 顺序被打乱（实测 33/33 文件段间连续性 `segBad = 段数-1`，即每条段与下一段都不相接）。

**里程账**：

```
sum officialKm (33 条)                     =  98,070 km
sum 主链 km（= points，API 实际渲染的）    =  29,332 km  =  官方的 29.9%
sum 孤段 km（= segments，已下载永不显示）  = 110,217 km  =  官方的 112.4%
```

**约 11 万公里已抓取、已落盘的公路几何永远不会被渲染。**

**里程坐标系也自相矛盾**：`gapAnnotations.atKm` 沿 `segments` 数组顺序累加，G318 实测范围 **1971~6246 km**，而 `points` 的 `cumKm` 只到 **1953.5 km** —— 断点标注的里程与实际渲染折线的里程是两套坐标系。且 `gapCount == segments.length`（33/33），即**每条公路的每一段都被算成了「断点」**，`engineNote` 显示「71 处未贯通」是虚高。

**其它错配（实测扫描全部 33 条）**：

| 现象 | 道路 |
|---|---|
| **6 条 0 景点** | G105、G106、G206、G207、G210、G326 |
| 跨 2522km 只匹配到 **1** 条景点 | G219（喀纳斯→东兴），主链 bbox 76.9~90.2°E 却声称终点在 108.1°E |

- **第一步（P0，1~2 人日）：把「假数据」改成「诚实的弱数据」**

### B3【P0】榜单「看沿程景点」加载失败 / 忽好忽坏

**现象**：从「中国最美公路」榜单点「看沿程景点 →」，有时正常显示，有时整页红色「加载失败」，刷新一下又好了。

**根因（四个叠加，按可能性排序）**：

**根因 1：`Promise.all` 原子失败（最直接）**

`DriveRoad.vue:113-116`：
```ts
const [roadData, alongData] = await Promise.all([
  api.getDriveRoad(code),
  api.getDriveAlong({ road: code, max: 200 }),
]);
```
- 558/591 条路 `hasGeom:false` → `getDriveRoad` 返回 `ok:true, geometry:null`（**不报错**），但 `getDriveAlong?road=X` 走 `drive.ts:139-142` 返回 **404**
- `request()`（`client.ts:15-22`）对 `ok:false` 一律 `throw`
- → `Promise.all` 整体 reject → 整页红字

**表现不是「景点为空」，而是整页「加载失败」** —— 与用户描述完全吻合。

**根因 2：限流 429（最像「忽好忽坏」的机制）**

`index.ts:68-69`：`const limit = isRailMutate ? 36 : 120;`，`/drive/*` 全部落入 `hitsGeneral` 桶（只有 `/rail-geometry/jobs/` 走独立桶）。`DriveHome.vue:62` 调 `/drive/network/overview` —— 服务端**一次读 33 个几何文件、`JSON.parse` 5.72MB、无缓存**（`roadNetwork.ts:141-162`）。多标签页 / 快速切页极易触顶 → 429 → throw → 「加载失败」。

**根因 3：`/drive/along` 无服务端缓存 + 同步 IO 阻塞**

- `geomCache` LRU `GEOM_LRU_MAX = 24`（`roadNetwork.ts:78`），但有 **33** 个几何文件 → 浏览 >24 条路后必然抖动，每次 miss 重新 `JSON.parse` 最大 596KB；
- `matchSpotsAlong` 跑在**未抽稀**的全量折线上（`drive.ts:181` 用 `route.coords`，抽稀在 `:193` **之后**）→ G318 4673 点实测 124ms；
- 单 Node 单线程 + 同步 `readFileSync`/`JSON.parse` 5.72MB → **期间阻塞整个事件循环**，其他并发请求超时。

**根因 4：高德在线 API 失败静默**

`roadRouting.ts:84-133`：`AMAP_KEY` 缺失 / 8s 超时 / `errcode!==0` / 网络抖动 → 全部 `return null` **无日志无提示** → 落到 `localDriveRoute`（实测 99% 也是 null）→ `engine='direct'`（两点直线）→ 直线走廊只能匹配到极少数景点（常常 0 条）。`AMAP_KEY` 已设置但高德有 QPS/配额限流 → **天然间歇性**。

**叠加的数据缺陷**：33 个条目中 22 个（67%）`roadKeys: []`，这 22 条里 **0 个**有 `fromPlace`/`toPlace` 兜底。`DriveBoard.vue:40-42` 因此退化成：
```ts
const from = item.fromPlace ?? item.province[0] ?? '';
const to   = item.toPlace   ?? item.province[item.province.length - 1] ?? '';
```
**同一省的条目会得到 `from === to`** → `planDriveRoute` 用同一坐标规划 → `lengthKm ≈ 0` → 沿程景点为空。而 `DriveBoard.vue:113-119` 的兜底提示**只在「有 roadKeys 但无几何时」显示**，这 22 条**得不到任何提示**。

**方案**：
1. `DriveRoad.vue:113-116` 改 `Promise.allSettled`，两个请求独立降级：几何失败只显示索引信息 + 「几何待补」；景点失败显示景点区错误 + **重试按钮**；
2. `DriveBoard.vue:33-43` 的 `alongHref` 三级兜底**必须校验 `from !== to`**，相同则禁用跳转并显示「该条目暂无 OD 数据」；
3. `/drive/network/overview` 加**进程级缓存**（`updated` 字段已经是天然的缓存键）+ 预抽稀结果缓存，彻底消除 5.72MB 重复 parse；
4. `GEOM_LRU_MAX` 从 24 提到 64（覆盖全部 33 条），或对 33 条几何做**启动期一次性预热 + 精简**（抽稀到 800 点存一份 overview 专用副本，5.72MB → 约 0.5MB）；
5. `matchSpotsAlong` 改为在**抽稀后**的折线上跑（把 `drive.ts:193` 的抽稀挪到 `:181` 之前），G318 实测 4673→600 点可将 124ms 降到约 20ms；
6. `/drive/*` 单独限流桶（参考 `hitsRailPoll`），或把 120/min 提升；
7. `amapDriveRoute` / `geocodeFallback` 的失败加**结构化日志**（不要空 catch），便于后续定位。

**工作量**：3 人日。

### B4【P1】沿程景点本身的数据错误（G318 景点混乱的直接原因）

### V1【P0】起点/终点输入框与「按公路编号直达」的遮挡与层级问题

**现象**：起点/终点输入框的下拉联想在某些情况下被卡片内容压住、或滚出卡片外不可见；与下方「按公路编号直达」区域的视觉层级混乱。

**根因分析（现状核查结论：不是简单的 z-index 数值问题，是多层叠加）**：

1. **`.station-suggest` 的 z-index 作用域受限**。`base.css:442` 给了 `z-index: 40`，但它的父级 `.station-field__control`（`base.css:436-438`）在 `.rv-card` 内部，而 `.rv-card` 有 `isolation: isolate`（`base.css:141`）—— **创建了新的层叠上下文**。所以 `z-index: 40` 只在卡片内有效，**压不过任何外部元素**（如 `.road-kbd` 卡片的 `::after` 光晕）。
2. **嵌套 backdrop-filter 弱化（代码注释已承认）**。`base.css:453-456` 明确记录：「父级 `.rv-card` 已有 backdrop-filter 时，嵌套 blur 在部分引擎会弱化，故底色需比 `--surface-1` 更实」。但兜底手段是：
   ```css
   background: color-mix(in srgb, var(--surface-0) 88%, transparent);
   ```
   `color-mix()` 在 Chrome 111+ / Safari 16.2+ / Firefox 113+ 支持，**旧 WebView（鸿蒙 ArkWeb 早期）不支持 → 整条声明失效 → 下拉完全透明 → 与卡片玻璃叠加后文字重叠**。
3. **无防溢出机制**。铁路 `SelectTrip.vue:806` 有 `has-suggest-open` 类在联想展开时提升卡片 z-index，**自驾 grep 0 命中**。
4. **OD 卡片与编号键盘卡片是兄弟 grid**（`DriveHome.vue:288` 与 `:352`，`drive.css:647-651`），DOM 顺序 OD 在前。当前布局下不重叠，**所以严格说「当前无实际遮挡 bug」** —— 但这是**脆弱的巧合**，一旦改成两卡上下堆叠（V1 方案里正好要这么做）或栅格重排就会立刻暴露。

**方案**（与 A5 的翻卡改造合并做）**：
1. **兜底背景不依赖 `color-mix`**：改用 `rgba()` 字面量或 `background-color: var(--surface-0); background-color: color-mix(...)` 双声明（不支持时自动回退到不透明底色）—— 一行改动，收益覆盖所有旧 WebView；
2. **补 `-webkit-backdrop-filter`**：见 V3；
3. **翻卡时加 `has-suggest-open` 等价类**，在联想展开时把当前卡片的 `z-index` 提到 50（高于 `.road-kbd` 的 30）；
4. **联想下拉加 flip 逻辑**：接近视口底部时向上展开（当前只向下，`:440-461`），移动端尤其需要。

**工作量**：1 人日（与 A5 合并）。
