> 日期：2026-10-12 ｜ 状态：**待人工评审**（本文是优化基稿，按旅行博主经验补充，等你逐段改）

## 0. 一句话目标

把「不一书旅行规划」Skill 的问答与核查骨架，嫁接到 RailVista 的数据与 API 能力上，做出**两个模式**：

1. **寻找目的地模式**（新增，差异化核心）——用户只有"想出去玩"，通过定制化问答 + 真实价格/时刻查询，推荐 3—5 个候选目的地并讲清为什么；
2. **确定目的地模式**（已有骨架完善）——目的地已定，产出全流程可执行攻略（大交通/小交通/门票/住宿/美食/体验项目/问题预案），页面**可编辑可调整**。

两端交付：**Web 端先行**，鸿蒙端二期；对话算力优先接**小艺开放平台**（LLM/工作流模式平台承担算力，开发者与用户均 0 成本），并保留可插拔降级。

## 1. 原材料分析：bys-travel-plan 强在哪、缺什么

### 1.1 直接继承的资产（这是它最值钱的部分）

| 资产          | 内容                                                                                                          | 对我们的意义                                  |
| ----------- | ----------------------------------------------------------------------------------------------------------- | --------------------------------------- |
| 阶段关口        | S0 能力发现 → S1 需求澄清 → S2 目的地决策 → S3 调研 → S4 对齐 → S5 规划 → S6 核查 → S7 交付 → S8 卡片 → S9 修改恢复                      | 成熟的状态机，S2 就是"寻找目的地"的雏形，需要加深             |
| 三大底线        | 不为完整编造数据 / 不为精确增加注册门槛 / 不为好看牺牲事实一致性                                                                         | 与 RailVista"不编造业务数据"的项目纪律同源，直接继承        |
| 单一数据源       | `trip.json` 唯一业务数据，MD/HTML/图片卡同源渲染，版本快照可回退                                                                  | "页面可编辑"的地基：改 trip.json → 重渲染，不是三个产物各改各的 |
| 证据分级        | `verified / experience / estimate / unknown / conflict`；路段 `tool_route / public_route / estimate / unknown` | 价格、时刻、开放时间全部带证据等级，正好承接"查不到就写未知"         |
| 方案状态三档      | `draft / conditional / executable_as_of_check`                                                              | 待预约、待放票的关键项不会伪装成"已安排好"                  |
| 核查脚本        | `validate_trip.py`（结构/算术/ID 引用/凭据扫描）、`state_io.py`（版本/存档）纯标准库                                               | 可直接复用，作为我们 API 侧的校验镜像                   |
| 单文件 HTML 手账 | 自包含、无 CDN、无远程调用、渐进增强、打印友好                                                                                   | Web 端交付物的标杆形态；升级为"可编辑版"见 §7             |

### 1.2 按旅行经验要补的缺口（本设计的重点）

- **S2 太薄**：只有"粗筛 → 3—5 候选 → 六件事"，没有**推荐引擎**：不讲天数/人数/交通方式/淡旺季人流的组合推理，不讲"独行者不该被推去青甘大环线"。
- **没有真实价格链**：机票比价（含中转与中转预留时间）、12306 时刻、景区门票、当地小交通的价格与时间计算缺失。
- **没有问题智库**：存包、偏远地区打车、抢票、高反、晕车、船班——老旅行者踩过的坑没有结构化沉淀。
- **没有体验项目层**：滑雪、飞拉达、潜水/浮潜、雪山俱乐部、租电动车、景区直通车、观景房/日照金山/星空等"小确幸"与体验选项。
- **缺出行方式对比**：自由行 / 拼小团 / 包车 / 跟团 的利弊与适合人群（含"一家人独立成团"方案）。
- **生成物不可编辑**：MD/HTML 是静态产物；用户要能改。

### 1.3 合规注意

- 上游是 MIT：Fork 进 RailVista 后**保留 LICENSE 与署名**，署名改为「基于 不一书旅行规划Skill（MIT）· RailVista 旅行规划生成」，渲染器写入 + 校验器检查（继承它"署名不靠模型记得加"的做法）。
- 上游明确"不订票、不支付、不预约"——继承。我们做规划与信息聚合，**不做交易**。

关键决策：

- **Skill 指令层与算力层分离**。Skill（怎么问、怎么排、怎么核查）是一份 Markdown 指令 + JSON schema，不绑死任何模型；小艺、自备网关都吃同一份指令，保证两端行为一致。
- **API 网关即"云插件"**。小艺的插件体系（Restful/SSE/WebSocket + AK/SK + 2.2s 超时）天然适配我们的 `/api/plan/*`；同一个网关同时服务 Web 端与鸿蒙端，不写两遍。
- **trip.json 仍是唯一业务数据源**，落在服务端（每行程一 ID），Web 编辑器与鸿蒙端都通过 API 读写它。

## 4. 模式一「寻找目的地」详细设计

### 4.1 入口与定位

用户信号："周末去哪""几天假不知道干嘛""预算 X 能去哪""一个人想去旅行"。入口即 S1/S2 合并加深：**先问对人，再谈目的地**。

### 4.2 定制化问答树（每轮 3—5 问，不一次全抛）

**第一轮 · 硬约束**

1. 从哪里出发（城市，不索要住址）？最早哪天走、最晚哪天回？
2. 一共几天 / 几个整天？（扣掉往返路上还剩多少可玩时间）
3. 几个人、什么构成？（单人 / 情侣 / 朋友 2—4 / 家庭带儿童 / 带老人 / 一家三代）——**人数构成直接决定目的地形态**，见 4.3
4. 预算口径：人均还是全队？含不含大交通？含不含购物？（对齐 skill 的预算口径规则）
5. 大交通接受度：高铁优先 / 飞机可接受 / 只接受自驾 / 无所谓？

**第二轮 · 偏好与弹性**

1. 兴趣标签（多选 + 排序）：自然风光 / 人文历史 / 城市繁华 / 美食 / 户外体验（徒步滑雪潜水）/ 拍照出片 / 避世松弛
2. 季节与淡旺季弹性：只能固定日期 / 可前后挪一周 / 可挑淡季错峰（淡旺季人流量与价格差异要说清）
3. 有没有明确排除项（高原、晕车严重、爬山、人多、太远）
4. 接受报团/拼小团/包车吗？（独行者尤其要问，见 4.3）

**第三轮 · 按需追问**（由前两轮结果触发，不普适全问）

- 带老人 → 日均步行强度上限、午休需求、就医便利性
- 带儿童 → 年龄段、推车/安全座椅
- 固定日期 → 是否接受"当周天气再微调"
- 预算紧 → 可否接受夜班火车/红眼航班/青旅

### 4.3 人数构成 → 目的地形态规则（旅行经验核心）

| 构成          | 推荐形态                                                         | 明确不推荐 / 需确认                                                           |
| ----------- | ------------------------------------------------------------ | --------------------------------------------------------------------- |
| 单人          | 自由行友好：公共交通成熟、青年旅舍/拼车文化成熟、治安好的城市与轻量级自然目的地；可接受"拼小团"体验项         | ⛔ 不主动推荐需包车/报团才能完成的大环线（青甘大环线、西藏深度、川西长线）——除非用户明确接受拼小团，且必须写出"拼小团"替代路径与利弊 |
| 情侣 / 朋友 2—4 | 自由行 + 局部包车/租车；高铁圈邻城深度                                        | 高原长线需确认驾驶经验与晕车耐受                                                      |
| 家庭带儿童 / 带老人 | 单基点少换宿、车程短、医疗便利、景区设施完善；可包车                                   | 高海拔、长车程、高强度徒步需显著提示                                                    |
| 一家三代 / 全家出动 | **独立成团（包团）方案**：一大家子包一辆车/一个团，行程自定义、节奏自控——把"包团 vs 散拼"的价格与利弊列清楚 | 散拼团人员随机、节奏不可控，需明示                                                     |

> "一家人站满团"（用户原话）在此落地为**独立成团**选项：预算允许时，包车/包团对家庭是体验与自由度的最优解，方案里必须给出包车日均价区间（标估算来源与查询时间）。

### 4.4 推荐引擎（3—5 候选，讲清"为什么是它"）

候选来源三层：① 路书库 147 条既有路线（按 tags/省份/天数匹配）；② 景点库 36893 条聚合出的区域热度（按兴趣标签）；③ 周边短途专项（出发地 2h 高铁圈/自驾圈）。

每个候选固定输出**七件事**（对齐并加深 skill 的六件事）：

1. 匹配理由（对应到用户具体输入："你说 3 天、预算人均 2000、带老人，所以…"）
2. 往返交通实测：高铁时刻与二等座价格（12306，预售期内）/ 航班时刻与价格（FlyClaw，含中转方案）
3. **扣除交通后的实际可玩时间**（小时数，不是"三天两夜"这种虚数）
4. 人均/全队预算区间（交通/住宿/门票/餐饮分项，已付未付分开，未知单列）
5. 淡旺季与人流：目标日期的季节画像、拥挤度预期、价格浮动（AI 联网核实 + 标注）
6. 主要缺点（"周末老城区人多""雨季封山"——必须写，候选不许只报喜）
7. 关键不确定性（预约规则、开放期、天气窗口）

### 4.5 价格与时间计算链（模式一的硬功夫）

- **机票**：`/api/plan/airfare` 去程+回程分别查；支持中转，中转预留时间规则（国内联程 ≥1.5h、跨境 ≥2h、换航站楼按 3h 起）；红眼/早班标注对首末日行程的影响；**多平台比价**（FlyClaw 飞猪源为底，AI 联网补充携程/同程等公开页面价，全部标来源+时间）；学生优惠资格在结果里标注（不替用户认证）。
- **火车**：12306 by-code；预售期外 NOT_FOUND 是预期 → 转"季节参考 + 抢票提醒"（预售 15 天、放票时间点进出发前清单）。
- **性价比口径**：不只看票价，算"门到门总耗时"（市区到机场/车站 + 班次密度 + 正点率口碑）；高铁 4h 内通常优于飞机，要说出为什么。
- **当地小交通**：景区直通车（贵州类）、船班（舟山类，班次+天气停航风险）、租电动车（桂林类）、顺风车/拼车（川西类）——进 `/api/plan/local-transit`，附官方公众号/页面链接（AI 联网核实当时市场环境，不写死）。
- **门票**：高德 POI + AI 联网核实，输出"门市价/预约价/优惠票种 + 预约入口 + 放票规则"，价格一律标查询时间；查不到写 unknown。
- **徒步线**：候选为户外向时，给 1—2 条成熟徒步线（GPX 里程/爬升/耗时，数据来自导入的公开轨迹，不虚构）。

## 5. 模式二「确定目的地」增补设计

原 skill 骨架（S3—S9）保留，增补六个模块：

### 5.1 出行方式对比（每次必出）

| 方式           | 适合                | 利弊                 | 价格口径          |
| ------------ | ----------------- | ------------------ | ------------- |
| 自由行          | 单人/情侣/城市与成熟景区     | 自由但全程自担规划成本        | 分项实查+估算       |
| 拼小团          | 独行者去需包车区域（川西/青藏类） | 解决交通但人员随机、节奏固定     | 日均价区间（估算）     |
| 包车           | 家庭/三代/老人          | 自由+省力，成本最高         | 日均价区间（估算，按车型） |
| 跟团           | 远线/免规划/长者         | 省心但购物点与节奏风险，需甄别纯玩团 | 报价区间（AI 联网）   |
| **独立成团（包团）** | 一家人/朋友整队          | 自定义行程+自由度，人均通常高于散拼 | 整团价区间（估算）     |

> 输出"利弊分析"而不是替用户决定；涉及增加费用/放弃必去项 → 走 skill 的决策关口（集中说明：发现了什么→影响→选择→建议）。

### 5.2 旅行问题智库（`problembank.json`，老玩家的坑）

| 问题      | 内容形态                                              |
| ------- | ------------------------------------------------- |
| 存包/寄存   | 车站/景区寄存点、价格区间、规则（大小件、夜间）、大件行李方案；问用户"带几件行李"        |
| 偏远地区打车  | 顺风车 / 拼车 / 旅游直通车 / 大巴的可行性排序 + 官方公众号或约车入口（AI 搜索核实） |
| 抢票      | 旺季铁路预售期与放票时间、候补策略、机票低价窗口；写进出发前清单（must 级）          |
| 高原反应    | 目的地的可就诊医院（如西藏）、药品准备、行程缓冲建议；不替代医疗建议                |

## 7. 可编辑行程页面设计

- **数据**：`trip.json` 存服务端（行程 ID = `日期-目的地-天数`），版本快照 + 变更摘要沿用 skill 的 `state_io` 理念（API 化）。
- **编辑器**（Web 端 Vue）：左侧行程时间轴、右侧编辑面板——改活动/时间/住宿/预算/清单；每次改动走依赖链检查（改住宿 → 当日首末路段 → 出发时间 → 预约可达性重查）；改完"保存为新版本"，旧版可回退。
- **渲染**：服务端渲染 MD + 单文件 HTML（离线可看、可打印，继承自包含/无 CDN/渐进增强规则）；编辑器与 HTML 共用同一 `plan_version`。
- **鸿蒙端**：同一 trip.json API，卡片式展示 + 语音修改（"把第二天上午换成室内"→ 局部更新）。

## 9. 红线与纪律（全部继承，写进 Skill 指令）
