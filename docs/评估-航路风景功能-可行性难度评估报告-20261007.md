> 日期：2026-10-07
> 版本：v1.0

## 1. 维度一：航路数据怎么搞

### 1.1 难点在哪

民航航班的**计划航路**（flight plan，含航路点 waypoint 序列、空域走廊）不对外公开免费获取：

- AIP China（中国民航航行情报）有航路结构公开资料，但获取、解析、持续维护成本高，且对"看风景"场景精度过剩；
- 国内航班的计划航路数据无任何免费 API；
- 民航航路也不是直线，是沿导航台/航路点折线，简单直连会有偏差。

### 1.2 可行方案（两层递进）

**第一层：机场对大圆航线（Great Circle）近似 —— 难度低**
- 机场坐标来自 OpenFlights.org 数据库（CC-BY 许可，免费下载 airports.dat，约 1 万+ 机场含 IATA/ICAO 码与经纬度）；
- 机场间用大圆公式采样成折线（`spherical-geometry.js` / `turf.js` 现成实现，或 shared 层手写 20 行）；
- 对"从万米高空看窗外的风景"场景，大圆近似与真实航路的横向偏差（通常 <50km）影响很小——航景的观看半径本来就是 60-100km 量级。

**第二层：ADS-B 历史轨迹聚合实际走廊 —— 难度中，强烈建议做**
- 思路与本项目**完全同构**：铁路折线是从 OSM 提取的，航路走廊可以从 ADS-B 历史轨迹聚合：
  - `fetch`：OpenSky `GET /tracks` + `/flights/aircraft` 按机型/机场对拉历史轨迹（免费注册，认证后 4000 credits/天）；
  - `build`：同一 OD 对的多条轨迹做聚类/中心线提取（buffer + 融合），生成 `data/airways/*.json`；
  - `verify`：复用现有质量门禁思路（osmRailway.ts 的 `acceptSegmentGeometry`：绕路比/端点距/横向偏离三门禁）；
  - `serve`：服务常驻内存装载（照搬 `corridors.ts` / `localRails.ts` 模式）。
- 建一条常用航线（如 PEK-SHA）拉 30-50 条历史轨迹即可得到稳定的"实际走廊"，之后作为该航线的默认几何。

### 1.3 数据管线复用度：高

现有 `scripts/` 约 130 个脚本族（fetch→build→fill→patch→audit→verify）的工程范式、落盘缓存基建（`data/cache/*`）、质量校验 playbook 全部可照搬为 `build-airway-corridor.mjs` 族。

## 2. 维度二：免费开放、安全稳定的航班查询 API

### 2.1 实测结果（2026-10-07 实测）

| 数据源 | 实测结果 | 费用 | 评价 |
|--------|---------|------|------|
| **OpenSky Network** | ✅ 匿名可用，华北 bbox 查询返回国内航班实时状态（实测返回 CHH7797、CBJ5531 等呼号的经纬度/气压高度/地速/航向/垂直速率） | 免费（匿名 400 credits/天，OAuth2 注册后 4000/天，给社区做数据馈送可升 8000/天） | 国际上最可用的免费实时航班数据源；**国内 ADS-B 覆盖密度不如欧洲**，干线机场周边有数据，偏远航段可能丢包，时间分辨率 10s（匿名） |
| adsb.lol | ❌ 实测 503 Service Unavailable | 免费 | 社区免费源，稳定性一般，不宜做主依赖 |
| airplanes.live | ❌ 实测返回需邮件申请 | 免费（需申请） | 非完全开放 |
| FlightAware AeroAPI | 收费（商业 API） | $$$ | 不符合"免费"要求 |
| Flightradar24 API | 收费 | $$$ | 不符合"免费"要求 |
| 航旅纵横 / 飞常准 / 携程 | **不开放 API**，仅有面向个人的 App | - | 国内航班动态数据的实际垄断者，数据来自空管 ADS-B + 航司合作，不对外开放 |

### 2.2 关键结论：换一个思路，这个维度的依赖可以整体消解

"免费 + 开放 + 稳定"三者兼得的国内航班实时 API **目前不存在**——这是事实，也是本功能最大的风险点。但请注意：

> **看风景场景本质上不需要实时航班动态 API。**

理由：用户坐哪个航班，用户自己最清楚。航旅纵横机上模式的核心逻辑也是：
1. 登机前（有网）：用户绑定航班号 + 日期，App 下载该航班的计划航路（或近似航路）+ 沿途数据；
2. 机上（无网）：手机 GNSS 芯片定位（不需要网络），在预下载的航路上做投影匹配，推算进度与 ETA；
3. 实时航班动态 API 的价值只在于"自动识别你坐哪个航班、不用手输"这个便利功能，以及"实际航迹 vs 计划航路"的修正——属于锦上添花。

因此建议的架构分层：
- **主链路（不依赖任何航班 API）**：手动输入航班号 / 从起降机场对选择 → 出发前打包行程 → 机上纯离线推算（见维度五）；
- **增强链路（可选，免费源）**：OpenSky 匿名/注册查询，用于 ① 出发前用当日该航班的 ADS-B 航迹修正计划航路；② 落地后回放；③ 航班号→机型→选座建议（靠窗/背对太阳）。
- **航班号→呼号映射**（CA1832 → callsign "CCA1832"）用 OpenFlights airlines.dat + 简单规则（航司 IATA 码 + 航班号）即可，免费数据足够。

### 2.3 OpenFlights 基础数据（免费无争议）

- `airports.dat`：全球机场（IATA/ICAO/坐标/海拔）；
- `airlines.dat`：全球航司（IATA/ICAO/呼号前缀）；
- `routes.dat`：全球航线网络（航司+起降机场）；
- 用途：机场选择器、航班号合法性校验、航司 logo 关联（本项目已有全航司 logo 资产，直接复用）。

## 3. 维度三：与天气结合的难度

### 3.1 实测结论：难度低，且现有架构几乎全复用

**实测 Open-Meteo（免费、无 Key、无墙）支持 250hPa 气压层查询**（≈10,400m，正处巡航高度区间）：

```
GET api.open-meteo.com/v1/forecast?latitude=..&longitude=..
  &hourly=cloud_cover_low,cloud_cover_mid,cloud_cover_high,wind_speed_250hPa,temperature_250hPa
→ 2026-10-07 实测返回正常（北京 39.9N,116.4E）
```

其中 **低云量 cloud_cover_low / 中云量 cloud_cover_mid / 高云量 cloud_cover_high** 三个分层字段对航景场景是"量身定做"的：
- 低+中云量 → 决定能否**俯瞰地面**（飞机在云上还是云下）；
- 高云量（卷云）→ 决定视野通透度；
- 各层风 → 可做"颠簸提示"的粗略参考（增强项）。

### 3.2 与现有代码的对接

现有 `apps/api/src/services/qweather.ts` 的架构完全通用，改动点极小：
- 0.1° 网格缓存（TTL 1800s）、批量 40 点并发 4、`auto` 模式双供应商 fallback —— 全部直接复用；
- 唯一改动：`fetchOpenMeteo` 的 hourly 参数扩展 pressure-levels 字段；输出结构 `SpotWeather {cond, visKm, cloud}` 增加 `cloudLow/cloudMid/cloudHigh/cruiseWind` 等字段；
- 和风天气无高空层（所有地面气象供应商都只给地面），所以高空统一走 Open-Meteo，无需纠结双供应商。

### 3.3 增强项（可选）

- 舷窗眩光/日出日落方位：太阳方位角计算纯几何（现有 shared geo 层可加）；
- 地形数据：Open-Meteo Elevation API / Copernicus DEM，用于"左侧 40km 处 XX 山，山顶现距航线垂直距离 XX km"的表达。

## 4. 维度四：景点问题

### 4.1 与铁路景点库的差异

从 9,000-12,000m 高空看到的风景与地面的景点库**重合度不高**：地面景点库（scenic-spots.json）以景区/观景台为单位，而航景需要的是**大尺度地理地标**。

### 4.2 航景库的构成（三类数据源，管线全部现成）

| 类型 | 示例 | 数据源 | 现成度 |
|------|------|--------|--------|
| 大型自然地标 | 大型山脉（秦岭、天山）、大湖（青海湖、鄱阳湖）、大河（长江、黄河）、沙漠（塔克拉玛干）、海岸线、大型峡谷/盆地 | Wikidata 大型地理实体（本项目已有 `build-scenic-wikidata-truths.mjs` 校验管线）+ OSM PBF 自然要素（water/ridge/natural=* 按面积长度阈值筛选，PBF 下载管线现成） | 高 |
| 人文大尺度 | 城市建成区灯海、大型梯田、水库、跨海/跨江大桥 | OSM place=city + Wikidata（世界遗产/5A 景区名录公开） | 高 |
| 特殊时刻 | 城市夜景（入夜后）、雪山日出、云海 | 纯计算（日落时刻 + 太阳方位）+ 天气云量联动 | 中 |

### 4.3 需要新建的部分

- **筛选规则**：按"可见尺度"建阈值（湖泊面积 > 100km²、河流长度 > 200km、山脉长度 > 80km 等），从现有 POI 池子里筛出"航景级"子集——一次性管线工作；
- **Schema 扩展**：现有 scenic schema（`on_track 3km / window 8km / distant 35km` 可见性分级 + `resolveSpotSide` 左右侧）扩展出航空字段：
  - `viewRadiusKm`：60-100km（高空可视距离远大于地面）；
  - `bestAltitudeM`：最佳观看高度层；
  - `portholeSide`：left/right（复用左右侧逻辑，改名舷侧）；
  - `nightOnly`：夜景类标记。
- **数量估计**：全国航景级地标约 600-1,500 个（远少于铁路沿途景点量级），构建成本可控。

### 4.4 难度：中

数据源与管线现成度高，主要工作量在筛选规则调参和逐条人工抽验（本项目铁路景点已有"位置校验 playbook"经验可平移）。

## 5. 维度五：用户易用性（机上无网 + 卫星定位）

### 5.1 关键技术事实：GNSS 定位不需要网络

用户问题的核心假设需要澄清一个关键事实：

> **手机 GNSS 芯片（GPS/北斗/GLONASS）接收卫星信号计算自身位置，完全不需要移动网络或 WiFi。** "无网"影响的只是把位置发给服务器和下载地图瓦片，不影响定位本身。

- 航旅纵横机上模式用的就是这个原理：飞行模式下手机 GNSS 芯片出位置 + 预下载的航图 + 本地推算；
- **手机芯片的 COCOM 限制**（防止用于导弹）：速度 >515 m/s **且** 高度 >18km **同时**超限才会被禁用。客机巡航约 250 m/s（900km/h）、10-12km 高度，**远低于限制，Android/iOS 均可正常输出 GNSS 位置**（此点已被航旅纵横等 App 大规模验证）；
- Web 端：浏览器 Geolocation API 在飞行模式下仍可从 GNSS 芯片取位，前提是**页面已提前加载**（无网时无法加载新页面）且授权了定位权限。

### 5.2 有没有现成开源项目？

**没有与"机上离线航景伴侣"完全对应的现成开源项目**（航旅纵横机上模式是闭源核心功能；Flighty/Flightradar24 App 亦闭源）。但所有**组件级**方案全部开源可得：

| 组件 | 开源方案 | 说明 |
|------|---------|------|
| 机上定位 | 浏览器 Geolocation API / Android LocationManager | 系统级能力，GNSS 芯片直出，无需网络 |
| 大圆航线计算 | turf.js / spherical-geometry.js | 现成库 |
| 位置→航线投影匹配 | **本项目自有**：`projectToRailway`（packages/shared/src/schedule/progress.ts:164-188）逐段点积投影 + 距离门限回退 | 领域无关算法直接复用，只需把门限从铁路的 800-5000m 放宽到航线场景 |
| 进度推算/ETA | **本项目自有**：`estimateSpotEtas` 双通道融合（时刻表通道 + GPS 速度通道指数加权 + σ 置信分档） | 运输方式无关，构建航班版 ScheduleCurve（机场对+计划起降时刻+巡航速度模型）即可 |
| 离线数据打包 | **本项目自有**：`tripCache.ts` IndexedDB 行程快照（最多 10 条、过期策略、恢复后升级精确折线的状态机） | 模式直接平移 |
| 地面 ADS-B 接收（长期增强） | dump1090 / readsb / tar1090（全开源） | 树莓派 + RTL-SDR 约 200 元自建接收站，feed OpenSky 可升级 8000 credits/天 |
| PWA 离线壳 | vite-plugin-pwa（Workbox） | 成熟方案 |

### 5.3 推荐的机上使用流程（与航旅纵横同构、与 RailVista 离线哲学一致）

1. **出发前（有网）**：输入航班号/选择机场对+日期 → 后端生成航路折线（大圆/走廊）+ 按航线缓冲区抽取航景库 + 天气预报快照（云量分层按小时）→ 一键打包进 IndexedDB；
2. **登机（无网）**：打开预加载页面，飞行模式下 GNSS 每 5-10s 出一次位置 → `projectToRailway`（航路版）投影 → 进度 = 沿线里程比 → `estimateSpotEtas`（航班版曲线）算下一个航景 ETA → 舷侧提示"预计 12 分钟后，右侧窗外出现青海湖，现在低云量 10% 视野良好"；
3. **落地后（有网）**：同步、回放、记录"这次航班看到的地标"清单（轻社交化可选）。

### 5.4 需要正视的两个工程点

- **PWA 从零引入**：当前 apps/web 不是 PWA（无 manifest、无 SW、无 vite-plugin-pwa）。机上无网场景要求页面壳离线可用，PWA 是必须的——工作量中等，路径成熟，但要做缓存策略设计（预缓存 App 壳 + 航路数据走 IndexedDB 而非 SW cache）；
- **浏览器授权与体验细节**：Geolocation 在 HTTPS 下需要用户授权；后台节流（横屏锁屏时 GPS 回调会被降频）需要做优雅降级（用推算补位——恰好 `estimateSpotEtas` 的双通道融合就是为此设计的）。

## 7. 总体难度矩阵与分期建议

### 7.1 难度汇总

| 维度 | 难度 | 风险等级 | 主要工作量 |
|------|:----:|:--------:|-----------|
| 1. 航路数据 | ★★★ 中 | 低 | 大圆航线（1-2 天）+ ADS-B 走廊聚合管线（3-5 天） |
| 2. 航班 API | ★★★★ 中高 → **架构绕开后 ★★** | 中（有绕行方案） | OpenFlights 基础库接入（0.5 天）+ OpenSky 可选增强（2 天） |
| 3. 天气结合 | ★ 低 | 低 | fetchOpenMeteo 扩参 + 字段透传（1-2 天） |
| 4. 航景库 | ★★★ 中 | 中 | 筛选管线 + schema 扩展 + 人工抽验（5-8 天） |
| 5. 机上易用性 | ★★★ 中 | 中 | PWA 引入（3-5 天）+ 打包流程 + GNSS 匹配联调（3-5 天） |

**整体评价：约 3/5。** 没有"从零发明"的部分——最难的实时数据问题恰好被架构绕开；工作量最大的是航景库内容建设（数据活，不是技术活），这与本项目铁路景点库的建设路径完全同构，团队已有成熟经验。

### 7.2 分期建议（风险递进）

- **M1（无外部 API 依赖，先跑通闭环）**
  机场对大圆航线 + OpenFlights 机场库 + 航景库 v1（Wikidata 大地标）+ Open-Meteo 云量分层 + 手动绑定航班出发前打包 + 机上 GNSS 离线匹配 + 舷侧/ETA 提示。
  → **这一期不依赖任何航班实时 API，没有免费数据源风险。**
- **M2（增强精度）**
  OpenSky ADS-B 历史走廊聚合（build-airway-corridor 管线）+ 出发前用当日 ADS-B 轨迹修正航路 + ETA 双通道融合接入。
- **M3（生态与体验）**
  PWA 完整化 + 自建 ADS-B feeder（dump1090，升 OpenSky 额度）+ 夜景/日出日落时刻联动 + 航班号自动识别增强。

### 7.3 成本

- 数据/API 费用：**0 元**（Open-Meteo 免费、OpenSky 注册免费、OpenFlights CC-BY、OSM/Wikidata 开放数据）；
- 唯一可选硬件投入：自建 ADS-B 接收站约 200 元（M3，非必需）。

### 7.4 最大风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| 国内 ADS-B 覆盖稀疏（OpenSky 对偏远航段丢包） | M2 增强精度打折 | 不影响 M1 主链路（计划驱动）；走廊聚合优先做干线热门航线 |
| 机上浏览器定位体验（授权/后台节流/部分机型 GNSS 冷启动慢） | 弱化实时感 | 双通道融合推算补位；提示用户"定位漂移时自动按时刻表推算"（铁路板块同一机制已验证） |
| 航景库筛选规则需要调参 | 内容质量 | 沿用铁路景点"生成→抽验→补丁"的 playbook，分省分期建设 |
| PWA 首次引入的工程量 | 工期 | vite-plugin-pwa 成熟方案，且 M1 可先以"出发前完整预加载"过渡 |
