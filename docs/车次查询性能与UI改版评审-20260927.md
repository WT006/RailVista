# 查询车次 — 性能优化与 UI 改版评审

> 日期：2026-09-27 ｜ 分支：`heyworldchannel-dev`（见第 4 节分支名核对）｜ 本文只做评审，**未改动任何代码**
> 结论先行：见 0.1 / 0.2；所有耗时均为本机实测或按代码常量推导。

---

## 0. 结论摘要

### 0.1 一句话结论

**「查车次慢」不是 12306 慢（实测 0.7s 内完成），而是每次请求都重复建会话 + 无超时兜底；「经停站慢」是本地车站坐标库只覆盖 38.4%，缺口走外部 Overpass/Nominatim 补全，且缓存命中仍会重跑补全 —— 最坏约 95 秒。**

### 0.2 实测基线（2026-09-27 本机）

| 环节 | 实测 | 代码位置 |
|---|---|---|
| `ensureSession`（`/otn/leftTicket/init`） | **314–437 ms，每次调用都执行** | `cr12306.ts:32` |
| 车次查询 `/otn/leftTicket/queryO` | **269 ms**（西宁→拉萨，7 趟） | `cr12306.ts:112` 循环 |
| 经停查询 `/otn/czxx/queryByTrainNo` | **90 ms**（Z323，7 站） | `cr12306.ts:180` |
| Overpass 批量补坐标 | **10.7 s（失败）/ 12 s（超时）× 3 个 URL ≈ 35 s** | `geocode.ts:277` |
| Nominatim 单站补坐标 | **6 s 超时** | `geocode.ts:336` |
| 高德补坐标 | 6 s 超时（未配 `AMAP_KEY` 则直接 null） | `geocode.ts:368` |
| 本地坐标库覆盖 | **1300 / 3388 = 38.4%** | `data/stations-geo.json` |

**推导的最坏耗时：**

```
查车次冷启：ensureSession 0.44s + query 0.27s ≈ 0.7s
           失败时串行试 5 个 path 且无超时 → 无上界（用户看到无限转圈）

经停站： ensureSession 0.44s + queryByTrainNo 0.09s
       + Overpass 3×12s ≈ 35s
       + 20 站 / 并发 4 = 5 批 × (Nominatim 6s + 高德 6s) ≈ 60s
       ─────────────────────────────────────────────
       最坏 ≈ 95 s，且「缓存命中」也会重跑这段
```

## 1. 性能诊断与优化

### 1.1 环节 A：输入站点 → 查询直达车次

#### 诊断

| # | 瓶颈 | 证据 / 现状 | 影响 |
|---|---|---|---|
| A-1 | **每次查询都重建会话** | `searchTrains`/`getStops` 开头都 `await ensureSession()`，无 TTL、无复用、无并发去重 | 固定 +300–440ms，占冷启耗时 60%+ |
| A-2 | **5 个 query 路径串行试探** | `QUERY_PATHS` 5 项，`for...of` 内 `await fetch`，仅失败才继续 | 失败场景 = 5×RTT ≈ 1.5–2.5s，且逐条累积 |
| A-3 | **完全无超时** | 12306 的 3 处 `fetch` 均无 `signal`（对比：`geocode.ts` 都已用 `AbortSignal.timeout`） | 上游挂起 → 前端**无限转圈**，无任何终态 |
| A-4 | **无负缓存** | 失败不写缓存，用户重试每次都付全价；且会持续冲击 12306 | 抖动期雪崩 |
| A-5 | **缓存脆弱** | 内存 `Map`，进程重启即失效；TTL 900s 无 SWR；过期瞬间全部回源 | 重启后首查必冷；热门 OD 过期后仍卡顿 |
| A-6 | **前端无取消/去重** | `api.searchTrains` 无 `AbortController`（只有 `getHealth` 有）；重复点击会并发 | 误触产生重复回源 |
| A-7 | 解析静默丢行 | `parseTrainRow` 硬门槛 `f.length < 30` 直接 `return null`，无埋点 | 偶发「查不到车」难排查 |

#### 优化方案

**A1 [P0] 会话复用与 in-flight 去重**
- 做法：`ensureSession` 改为模块级 `Promise` 单例 + Cookie TTL（建议 20–30 min）+ 并发请求共享同一次 init。
- 预期收益：冷启 0.7s → 0.3s（**-45%**）；命中会话时 ≈0ms；降低 12306 风控概率。
- 改动范围：`apps/api/src/services/cr12306.ts` 内 `ensureSession`（约 20 行），仅新增模块级变量，**不外溢到其它文件**。
- 风险：cookie 失效需能被 401/空结果触发强制刷新（保留 `force` 参数）。

**A2 [P0] 全链路超时 + 快速失败**
- 做法：新增 `fetch12306(url, {timeoutMs})` 小工具（建议单请求 4s、整体 6s）；`QUERY_PATHS` 循环加总预算；超时统一抛 `UPSTREAM_TIMEOUT`。
- 预期收益：最坏耗时 **从无界收敛到 6–8s**；前端必有终态。
- 改动范围：`cr12306.ts`（约 25 行）；工具函数建议放**新文件** `apps/api/src/services/http.ts`，避免污染共享模块。
- 前端配套：SelectTrip 侧 8s 后切换为「可取消的慢速态」（见第 2 节失败/超时态）。

**A3 [P1] 路径探测改并发择优**
- 做法：`queryO` 优先；失败后 `Promise.any` 并发试探 `queryG`/`queryA`（最多 2 条），而非 5 条串行。
- 预期收益：失败场景 **1.5–2.5s → ~0.5s**。
- 改动范围：`cr12306.ts` `searchTrains` 循环（约 15 行）。
- 风险：瞬时并发上升 → 必须与 A2 超时 + 现有限流（120/min/IP）同时上线。

**A4 [P1] 缓存分层 + SWR + 负缓存**
- 做法：TTL 按日期远近分层（今日/D+1：300s；D+2~D+7：900s；更远：3600s）；过期后先返旧值再后台刷新（SWR）；失败写 30s 负缓存；LRU 上限（如 2000 条）。
- 预期收益：热门 OD 二次查询 **≈0ms**；上游抖动期间仍可返回数据；失败重试不再反复回源。
- 改动范围：`apps/api/src/services/cache.ts` 新增 `getStale`/`setNegative`/`getOrLoadSWR`（约 40 行，**新增方法、不改现有 `get`/`set` 签名**）+ `cr12306.ts` 调用点。

**A5 [P2] 缓存持久化 / 预热**
- 做法：车次结果落盘 `data/cache/trains-*.json`，重启后热启动。
- 预期收益：重启后首查不冷。
- 改动范围：**新建** `apps/api/src/services/trainsCacheStore.ts`（**不要改 `preciseRouteCache.ts`**，该文件与景点/轨道线流程共用，属 tree 的战场）。
- 注意：车次余票/时刻随时间变化，落盘 TTL 需短（≤10min）且仅存时刻表。

**A6 [P2] 前端去重与取消**
- 做法：`api.searchTrains` 支持 `signal`；SelectTrip 维护 in-flight 请求句柄，新查询取消旧的；按钮 `loading` 期间禁用。
- 预期收益：消除重复回源与竞态（当前 `pickTrain` 连点会并发拉经停）。
- 改动范围：`apps/web/src/api/client.ts`（新增可选 `signal` 参数）+ `SelectTrip.vue`。

**A7 [P2] 解析可观测性**
- 做法：`parseTrainRow` 丢弃行时计数并 `console.warn`；`resolveTelecode` 的兜底 `suggestStations(q,1)`（3388 条全表扫描）加 Map 直查短路。
- 预期收益：微秒级性能收益，主要是排障能力。
- 改动范围：`cr12306.ts` + `apps/api/src/services/stationIndex.ts`（各约 5 行）。

### 1.2 环节 B：选中车次 → 加载经停站（含时刻、车站坐标）

#### 诊断

| # | 瓶颈 | 证据 / 现状 | 影响 |
|---|---|---|---|
| B-1 | **缓存命中仍重跑坐标补全** | `cr12306.ts:164-170`：命中缓存后 `await enrichStopsCoords(cached)` —— 只要有缺坐标站，就再走一遍远程 | **二次加载同样慢 30–95s**，缓存形同虚设 |
| B-2 | **补坐标阻塞在请求主链路** | 时刻表（90ms）与坐标补全（最长 95s）串行在同一个 `getStops` 里返回 | 用户为一个慢字段等全部 |
| B-3 | **远程补点超时/预算过宽** | Overpass 12s × 3 URL；Nominatim 6s + 高德 6s；预算 `REMOTE_GEO_MAX=20`、并发 4 → 5 批 | 最坏 ≈ 95s |
| B-4 | **外部服务不可达时无快速降级** | 实测 Overpass / Nominatim **全部超时**；`overpassTracker` 虽有 `localOnly` 降级，但阈值 2 次失败前仍会全价重试 | 网络劣化时每次都付满 |
| B-5 | **本地覆盖率仅 38.4%** | 1300/3388；大站命中、中间站大量缺失 | 长途车必然走远程补全 |
| B-6 | 重复点击无去重 | `pickTrain` 每次都发新请求 | 并发放大 |

#### 优化方案

**B1 [P0] 缓存命中即短路，版本驱动失效**
- 做法：
  - 命中缓存 **且** 坐标齐全 → 直接返回（不再 `await enrichStopsCoords`）；
  - 仅当「`stations-geo.json` 的 mtime/hash 变化」或「存在缺坐标站」时才重算；
  - 重算改为**后台异步预热**，不阻塞当次响应。
- 预期收益：二次加载 **30–95s → <50ms**；这是**单项收益最大**的改动。
- 改动范围：`cr12306.ts` `getStops` 缓存分支（约 10 行）+ 新增 geo 版本 fingerprint（可复用 `services/versionFingerprint.ts` 的既有思路）。
- 说明：现有注释「始终再 enrich 是为了覆盖缓存里的飞点」—— 该诉求由「版本变化即失效」等价满足，能力不丢，性能不再付代价。

**B2 [P0] 两段式返回：先时刻表，后坐标**
- 做法：`getStops` 只做「本地坐标匹配 + 时刻表」，缺坐标站返回 `coordStatus: 'pending'`；新增轻量异步任务/端点 `POST /api/trains/stops/enrich` 补齐坐标，前端增量合并（标记 `unresolvedStops` 已有先例可参考）。
- 预期收益：经停首屏 **30–95s → 0.5–1.5s**，感知提升最大。
- 改动范围：**新建** `apps/api/src/services/stopsEnrich.ts` + `routes/trains.ts` 新增端点 + `SelectTrip.vue` 增量合并逻辑。
- ⚠️ **不要复用 `railGeometryJob.ts`**（tree 主战场），另起轻量实现。

**B3 [P0] 收敛远程补点超时与预算**
- 做法：Overpass 单 URL 6s + 最多 1 次重试（总上限 ~12s）；Nominatim/高德合并 deadline 8s（`Promise.race`）；`REMOTE_GEO_MAX` 20 → 8（首末站 + 均匀抽样）；并发 4 → 6。
- 预期收益：最坏 **95s → ~20s**。
- 改动范围：`apps/api/src/services/geocode.ts` 常量与补点循环（约 30 行）—— **只改超时/并发/预算，不改匹配规则与 `rememberGeo` 语义**。

**B4 [P1] 预取 + 并行**
- 做法：`queryByTrainNo` 与本地 geo 匹配并行；前端在车次卡片 hover/focus 时预取 `/trains/stops`，选中时直接用。
- 预期收益：选中后等待再降 **30–60%**。
- 改动范围：`SelectTrip.vue`（新增 `hoverPrefetch`，需节流，避免撞 120/min 限流）。

**B5 [P1] 离线补全坐标库（治本）**
- 做法：用现有 scripts 体系离线批量补全，目标覆盖率 **38.4% → 80%+**；运行时不再远程补点。
- 预期收益：B3 的远程调用几乎不再触发，是**唯一根治**方案。
- 改动范围：`scripts/` 新增离线脚本 + 数据文件。⚠️ 数据落点用**新文件** `data/stations-geo-extra.json`，原因见第 4 节。

**B6 [P2] 分阶段打点**
- 做法：记录 `本地命中率 / overpass 耗时 / 远程补点数 / 总耗时`，一行结构化日志。
- 预期收益：后续定位不再靠猜。
- 改动范围：`geocode.ts` + `cr12306.ts` 加计时（约 20 行）。

## 2. 加载动效设计：复兴号 CR450AF 沿轨道行进

统一为**一个组件** `RailProgressLoader.vue`，查询车次与加载经停站两处复用（仅文案与阶段锚点不同）。
列车按**复兴号 CR450AF** 实车特征绘制（超长流线型鼻锥 + 银白车身 + 中国红腰线），不使用卡通小火车或 emoji 占位。

### 2.1 结构

```
┌────────────────────────────────────────────────┐
│  ●━━━━━━━━━━━━━━━━━━━[CR450AF]━━━━━━━━○        │  ← 轨道 + 复兴号车头
│  始发        查询中        解析         到达     │  ← 里程碑点（3–4 个）
│                                                │
│  正在查询直达车次                        62%    │  ← 主文案 + 百分比
│  向 12306 请求车次列表 · 通常 1–3 秒            │  ← 副文案
└────────────────────────────────────────────────┘
```

- **轨道**：宽 `min(92vw, 340px)`、高 6px、圆角 999px、槽色 `rgba(148,163,184,.22)`；槽内每隔 10px 一条枕木（低对比竖纹）。
- **已行驶段**：渐变 `#38bdf8 → #7dd3fc`，叠加 0.9s 流光（linear-gradient 位移）。
- **里程碑点**：未达 `#475569` / 已越过 `#38bdf8` / 当前点 1.4s `pulse`。

#### 列车造型：复兴号 CR450AF（车头朝右，侧视）

> 不要用 emoji（🚂）或「方块 + 圆窗」的卡通简笔画占位 —— 那是上一版难看的主因。按 CR450AF 实车特征画一笔成型的 SVG（viewBox `0 0 62 24`）：

### 2.2 动画节奏（关键：不做匀速假进度）

- **进度推进**采用「**阶段锚点 + 指数逼近**」：
  - 收到真实阶段事件 → 直接跳到对应锚点（过渡 0.45s `cubic-bezier(.22,.61,.36,1)`）；
  - 未收到事件 → 每 300ms 向下一锚点前进剩余距离的 8%，**上限 92%**（避免「假满 100% 后卡住」）。
- **车轮**：`rotate 0.6s linear infinite`，速度随阶段变化（查询 1×、补坐标 0.6× 慢行）。
- **车厢**：轻微上下浮动 `1.2s ease-in-out`，幅度 ≤1.5px。
- **阶段锚点（查询车次）**：0–15% 建立会话 → 15–55% 请求车次 → 55–85% 解析列表 → 85–100% 即将呈现。
- **阶段锚点（经停站）**：0–10% 读取行程 → 10–45% 获取时刻表 → 45–80% 匹配车站坐标（n/m）→ 80–100% 校对站序。

### 2.4 状态文案

> 全部改写为中性、正向的铁路用语。**已删除**「没赶上这趟车」这类带错失/不吉利的表达；重试按钮统一为「重新发车」。

| 态 | 主文案 | 副文案 | 操作 |

| 查询中 | 正在查询直达车次 | 向 12306 请求车次列表 · 通常 1–3 秒 | — |

| 失败 | 前方临时停车 | {中性描述，如「12306 暂时没有响应」} | 重新发车 |
| 完成 | 已为你找到 {n} 趟车 | — | — |

- 中性描述示例：`12306 暂时没有响应` / `网络好像断开了` / `车站坐标还在补齐`（**不写**"失败""错误""没赶上"）。

## 3. 整体 UI 美化建议

### 3.1 布局

- **两栏化**：`≥1024px` 时「左：查询表单 + 最近访问」／「右：车次结果 / 经停时间轴」；`<1024px` 保持单列，结果区吸顶。
- **车次列表**：由纵向堆叠改为 **2 列卡片网格**，卡片内四层信息——
  1. 车次号 `18–20px / 700`（左侧 2px 类型色条：G/D 蓝 `#38bdf8`、C 青 `#22d3ee`、Z/T/K 灰绿 `#94a3b8`）；
  2. 时刻 `出发 → 到达`，数字用 `font-variant-numeric: tabular-nums` 防跳动；
  3. 历时 + 日期 `12px` 次级色；
  4. 选中态：色条加粗 + 微阴影抬升（**不做位移抖动**）。
- **经停站展示（当前最弱环节）**：现 `step='od'` 只有两个 `<select>`，信息量为零。改为 **垂直时间轴 + 站点列表**：每站显示 序号 / 站名 / 到·发时刻 / 停留时长 / 跨日 `+1` 徽标；上下车站改为**在时间轴上点选**（替代两个下拉）；缺坐标站显示虚线圈 + 「坐标待补」。

### 3.2 配色与信息层级

- 收敛为 3 个 token，替换各页面硬编码散色：
  ```
  --rv-accent: #38bdf8;  --rv-accent-soft: rgba(56,189,248,.14);  --rv-danger: #fca5a5;
  ```
- 层级：页面标题 > 车次号 > 时刻 > 元信息（`16 / 20 / 15 / 12px`）；间距统一 `4 / 8 / 12 / 16 / 24`；卡片圆角统一 `12–14px`。
- 保持现有深底 `#0f172a / #152033`，**不建议**此时切换浅色主题（工作量大且易与 tree 的地图/景点样式冲突）。

### 3.3 微交互

- 结果项 **stagger 入场**：每项 +40ms，最多 8 项后取消延迟。
- **空态**升级：当前只有一行红字「未找到直达车次」，改为给两个行动按钮 —— 「换一天」/「试试演示线路」。
- 加载期间：列表区保留**骨架卡片**（3 张 60% 透明度占位），配合第 2 节的动效，避免整页遮罩造成的「空白恐慌」。
