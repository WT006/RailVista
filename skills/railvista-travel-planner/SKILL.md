# RailVista 旅行规划 Skill

本 Skill 基于 **不一书旅行规划 Skill（bys-travel-plan，MIT）** 的阶段机与三大底线，
结合 RailVista 自有的交通与地理数据资产重构。**方法论部分沿用并尊重原作者署名要求**（见 `references/redlines.md`）。

## 0. 能力总表

| 能力域       | 能做什么                                   | 数据口径（**必须原样标注，不得美化**）                                            |
| --------- | -------------------------------------- | --------------------------------------------------------------------- |
| 航班          | 按航线查去程/回程（含中转）、含价格                   | RailVista `/api/flights/search`（源：飞猪 FlyClaw），**含税与否、含行李与否以接口返回为准** |
| 火车          | 车次、时刻、席别余票                             | RailVista `/api/trains`（源：12306），**预售期约 15 天**，超期 NOT_FOUND 属预期         |
| 自驾/公路      | 任意两点公路路径、里程、耗时                          | RailVista `/api/drive`，本地公路网 A*，拓扑约 148.9 万节点；失败降级直线，须写明"直线估算"          |
| 景点/POI    | 景区位置、分类、评分、开放时间                          | RailVista 沿路景点库，36893 条；**开放时间约 69% 有值，无值即写"未知"**                       |
| 成熟路线       | 已编排好的多日路线（节点 + POI + 逐日计划）              | RailVista 路书库，147 条 / 覆盖 31 省（台湾、香港、澳门无覆盖，直接写明缺失）                     |
| 天气          | 目的地历史同期/预报天气参照                          | RailVista qweather 通道                                                    |
| 行政区划       | 出发地/目的地城市与区县的规范名与归属                      | RailVista `places-admin`（3564 条 = 34 省 / 384 地级 / 3146 区县）                |

> **口径说明**：以上每一条都比"网上有人说"可信，但**都不是官方售票/营运商的实时权威接口**——
> 所以凡是给用户看的票价与时刻，**必须同时给出 source 和 as-of 时间**，并在答疑中说明"以官方渠道为准"。

## 1. 两个模式（按用户输入自动选，不确定就问）

### 模式一 · 寻找目的地

用户信号：只有模糊出行意图（"周末去哪""预算 2000 能去哪""一个人想去旅行"）。
**先问对人，再谈目的地**（详见 `references/intake.md`）。

**第一轮 · 硬约束**（不分批，一口气问完会劝退，控制在 3—5 问一轮）

1. 从哪里出发（只要城市，不索要住址）；最早哪天走、最晚哪天回
2. 一共几天 / 几个整天（**扣掉往返路上还剩多少可玩时间**——这是决定成败的数字）
3. 几个人、什么构成：单人 / 情侣 / 朋友 2—4 / 家庭带儿童 / 带老人 / 一家三代
4. 预算口径：人均还是全队？含不含大交通？含不含购物？
5. 大交通接受度：高铁优先 / 飞机可接受 / 只接受自驾 / 无所谓

**第二轮 · 偏好与弹性**

1. 兴趣标签（多选排序）：自然风光 / 人文历史 / 城市繁华 / 美食 / 户外体验 / 拍照出片 / 避世松弛
2. 日期弹性：只能固定日期 / 可前后挪一周 / 可挑淡季错峰
3. 明确排除项（高原、晕车、爬山、人多、太远）
4. 是否接受报团 / 拼小团 / 包车

**第三轮 · 由前两轮触发的按需追问**（不普适全问）

- 带老人 → 日均步行强度上限、午休需求、就医便利性
- 带儿童 → 年龄段、是否需推车/安全座椅
- 固定日期 → 是否接受"临近按天气微调"
- 预算紧 → 可否接受夜班火车 / 红眼航班 / 青旅

**推荐形态的硬规则**（写进了 `references/destination-rules.md`，逐条执行）：

- **单人**：⛔ 不主动推荐需包车/报团才能完成的大环线（青甘大环线、西藏深度、川西长线）。
  确需自驾/包车的线路，必须同时给出"拼小团"替代路径 + 利弊 + 大致人均
- **情侣 / 朋友 2—4 人**：自由行 + 局部包车/租车；高原长线须确认驾驶经验与晕车耐受
- **家庭带儿童 / 带老人**：单基点少换宿、车程短、医疗便利、景区设施完善
- **一家三代 / 全家出动**：**优先给独立成团（包车/包团）方案**，与散拼团对比价格与节奏可控性

**每个候选输出固定的七件事**（缺一件就是没做完）：

1. **匹配理由**——必须回扣用户原话（"你说 3 天、人均 2000、带老人，所以排除了 XXX"）
2. **往返交通实测**——高铁时刻+二等座票价（12306，预售期内）/ 航班时刻+价格（含中转方案）
3. **扣除交通后的实际可玩小时数**——不许写"三天两夜"这种虚数
4. **预算分项**——交通/住宿/门票/餐饮，已付未付分开，未知单列
5. **淡旺季与人流**——seasonality 画像、拥挤度预期、价格浮动（联网核实后标注来源时间）
6. **主要缺点**——必须写。"周末老城区人多""雨季可能封山"
7. **关键不确定性**——预约规则、开放期、天气窗口

### 模式二 · 确定目的地

用户已选定目的地，进入逐日编排（详见 `references/planning.md`）。原 bys 的 S3—S9 阶段机保留，
增补六个模块：出行方式对比、旅行问题智库、体验项目库、住宿与观景小确幸、可编辑生成页、出发前清单。

## 2. 价格与时间计算链（Skill 的硬功夫，详见 `references/budget-time.md`）

### 机票

- 去程、回程**分别查**（很多人只查去程，回程踩坑）
- 支持中转，中转预留规则：**国内联程 ≥1.5h、跨境 ≥2h、需换航站楼按 3h 起**；
  低于阈值必须在结果里标"中转时间偏紧，误机需自行承担"
- **多源比价**：RailVista 接口为底，联网补充其他公开渠道，**全部标 source + as-of**
- 红眼/早班机必须标注对首末日行程的影响（"凌晨到，第一天只能算半天"）
- **回程时间算法**：以最晚返程日下午/晚上为界倒推，预留前往机场/车站市区交通 + 安检/取票时间，
  再倒推最后一整天的结束点。**不许推荐"最后一晚住景区、第二天早上赶 6 点车"这种方案而不警告**
- 学生票资格在结果里提示，但不替用户认证

### 火车

- 12306 by-code 查询，**预售期约 15 天**，超期返回 NOT_FOUND 属**预期行为**，不是 bug
- 超期时的正确处理：给出"季节参考运价 + 抢票提醒"，并把放票时间点写进出发前清单
- 高铁 ≤4h 通常优于飞机（含门到门总耗时），要说出为什么

### 性价比口径

不只看票价，算**门到门总耗时**：市区→机场/车站 + 班次密度 + 正点率口碑 + 安检时间。

### 当地小交通

景区直通车、船班（班次 + 天气停航风险）、租电动车、顺风车/拼车，这些不同 everywhere，
必须联网核实**当时当地**的实际运营情况并附官方页面链接，**不许写死成"一般有""通常有"**。

### 门票

输出"门市价 / 预约价 / 优惠票种 + 预约入口 + 放票规则"，价格一律标查询时间；查不到写 `unknown`。
**⛔ 内容红线：票价只陈述不代买，时刻只给量级不给承诺，里程必须标"估算口径"。**

## 3. 三大底线（继承 bys，违反即方案作废）

1. **不为完整而编造数据**：票价、开放时间、路程时长查不到就写"未知"，不写 0、不写"正常开放"
2. **不为精确而增加注册门槛**：不要求用户注册地图/天气/酒店 API；先用宿主已有工具，再联网，再保守估算并标注
3. **不为好看牺牲事实一致性**：Markdown、HTML、图片卡必须来自同一份行程数据

详见 `references/redlines.md`。

交付 Markdown 攻略 + 可离线打开的单文件 HTML（后续可选图片行程卡），**所有产出来自同一份数据快照**。
